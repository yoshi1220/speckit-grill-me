# SpecKit Grill Me

目的：アクティブな機能仕様にある曖昧さや未決定事項を検出・削減し、明確化すること。

本ファイルの「面談規律（全ラウンド共通）」に従い、`/speckit-clarify` の仕事を上限なしにやり切る。spec.md の曖昧さを検出し、**いま聞ける質問（フロンティア）をラウンドとして管理しつつ 1 問ずつ順番に**問い、回答を spec.md に即時反映し、**全論点（decision point）が Clear / Resolved / Outstanding / Deferred のいずれかに確定し、ユーザーが納得するまで**ラウンドを繰り返す。

> **※ 用語（設計ツリー / 質問候補一覧 / フロンティア / ラウンド / カテゴリ / 論点状態 / カテゴリ集約状態 / カバレッジマップ 等）については「用語集」を参照。**

**macOS / Linux + Bash 環境で `/speckit-clarify` の代替として実行できることが要件。** 対応環境内では、clarify が生成する成果物・副作用（`## Clarifications` セクション、各セクションへの反映、書き込みごとの検証、`checklists/requirements.md` の再検証、extension hooks の処理、カバレッジ付き完了報告）を同じ形式で生成し、明確化ワークフローの違いは徹底度だけにする。

この互換性は**成果物と副作用**に対するものであり、公式 SpecKit の全実行環境に対応する代替を意味しない。前提スクリプトは Bash 版に固定し、PowerShell / Python 版の自動選択やフォールバックは行わない。

## 言語設定

**ユーザーから別言語の指定がない限り、日本語でコミュニケーションする。** 質問、説明、進捗、spec.md は同じ言語で統一する。

## User Input

```text
$ARGUMENTS
```

## 前提

1. 実行環境が macOS / Linux で、`bash` コマンドと `.specify/scripts/bash/check-prerequisites.sh` が利用できることを確認する。満たさなければ、このスキルの対応環境外であることを明示して中断する。PowerShell / Python の別スクリプトへ切り替えない。
2. リポジトリルートで `bash .specify/scripts/bash/check-prerequisites.sh --json --paths-only` を **1 回だけ**実行し、`FEATURE_DIR` / `FEATURE_SPEC` を取得する。JSON が取れなければ中断し、`/speckit-specify` の再実行か feature ブランチ環境の確認を案内する。
3. spec.md が無ければ中断し、`/speckit-specify`の先行実行を案内する（ここで spec を新規作成しない）。
4. `.specify/memory/constitution.md`（プロジェクト原則）があれば読む。加えて、**存在するもののうち作業対象に関係する資料だけ**を通常のファイル検索・読み取り・シンボル検索で調べる:
   - `README*` / `CONTEXT.md` / `CLAUDE.md` / `AGENTS.md` / `documents/**` / `docs/**` — ドメイン用語、ステークホルダー、業務フロー、設計判断
   - 関連する既存 spec / plan / ADR — 既存要件、制約、採用済み・棄却済み判断
   - ソースコード / スキーマ / migration / model / interface / test — 実装済みの振る舞い、データ形状、境界条件
   - package / build / CI/CD / deployment 設定 — 技術スタック、実行環境、外部連携、運用制約

### Extension hooks（clarify と同一の処理）

`.specify/extensions.yml` があれば、質問開始前に `hooks.before_clarify`、完了報告前に `hooks.after_clarify` を処理する（無い・パース不能なら黙ってスキップ）:

- `enabled: false` のフックは除外（`enabled` 未指定は有効扱い）
- 非空の `condition` を持つフックは評価せずスキップ（HookExecutor に委ねる）
- コマンド名のドットはハイフンに変換（例: `speckit.git.commit` → `/speckit-git-commit`）
- `optional: false` → `EXECUTE_COMMAND: {command}` を出力し、実際にそのフックを現在のエージェント／セッションで起動して完了を待つ。出力だけで実行済みとみなさない
- `optional: true` → コマンド・説明・プロンプトを提示するだけ

## 用語集

本ファイル共通の用語。以降の Step はこの定義を前提に書いている。

### 設計ツリー

spec に残る未確定の決定（決めるべき論点）を、依存関係で親子につないだ木。面談の進行管理用にセッション内部で維持するモデルで、ファイルには書き出さない。

- **ノード** — 1 つの決定。セッション上の状態として、作業中の未解決（カバレッジの Partial / Missing）、確定（Resolved）、終端保留（Outstanding / Deferred）のいずれかを持つ。終端保留は今回の面談を閉じる状態であり、プロダクト上の決定が確定したことを意味しない。ユーザーの回答（または調査で判明した事実）で確定する。
- **枝** — 「親の決定が確定して初めて、子の決定が意味を持つ」という依存関係。例: 「対象範囲に◯◯を含めるか」（親）が決まらないうちは、「◯◯の一覧に何を表示するか」（子）は答えようがない。

質問候補一覧の各候補は、この木のいずれかの決定を確定させるための質問。初期形は Step 1 で作った質問候補一覧の各候補を Step 2 でノードと紐付けた時点にでき、以降は一覧に候補が増えるたびに対応する決定がノードとして加わり、回答・事実の確定でノードの状態が更新されていく（最初に作って固定する木ではない）。

親ノードが確定するたび、直下だけでなくすべての子孫ノードについて、その親決定の結果でも論点が成立するか、以前は成立しなかった論点が再び成立するかを両方向に再評価する。親依存を理由に子孫を非適用または終端保留へ変更する前に、その時点の論点状態・確定値・質問候補を「再開用情報」として現状態とは別に退避する。

成立しなくなった子孫は削除せず、**「非適用」という確定結果を持つ Resolved ノード**として残し、次を同じ処理内で行う。

- 対応する質問を現在のフロンティアと質問候補一覧から除く
- カバレッジマップ上の対応論点を Resolved へ変更し、「親論点〈論点〉の決定〈結果〉により非適用」のように根拠を記録する
- spec に子論点の古い記述が残る場合は、親を確定させた情報源に応じて Step 4A または Step 4B で削除・修正し、保存・検証する。親回答の Clarifications 記録とは別に、非適用になった子の Q&A は追加しない
- 設計ツリーとカテゴリ集約状態を再計算する

逆に、親決定の変更で、非適用または親依存の Outstanding / Deferred だった子孫が再び成立する場合は、親依存の終端理由を取り除いて次を行う。

- 退避した確定値が親の新しい結果でも有効で、現在の spec に反映・検証済みなら Resolved を維持する
- それ以外は、現在の spec と再開用情報から Partial / Missing を判定し直し、対応する質問候補を復元する。復元した候補には Step 2 の事実ゲート・影響度基準・依存関係評価を通常どおり適用する
- 再評価後のノード状態とカバレッジ状態を同じ処理内で更新し、設計ツリーとカテゴリ集約状態を再計算する

### 質問候補一覧

曖昧さスキャン（Step 1）で Partial / Missing の論点から作る、ユーザーに問う質問候補の全体プール。固定ではなく、追撃質問・決定の派生チェック・確定後の掘り下げ・再スキャン（Step 5）で候補が増え、調査で事実と判明した候補・既出回答で無効化された候補は落ちる。

### 質問候補の追加経路

質問候補一覧に候補が増える 4 つの経路。

| 経路                     | 説明                                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **追撃質問**             | 回答が曖昧・矛盾だったとき、同じ決定を精密になるまで問い直す質問（記録済みの決定との矛盾確認もこの形で出す）                                               |
| **掘り下げ**             | 選択肢が選ばれた結果として新たに生まれた決定点・境界条件を、納得まで確定させにいく質問                                                                     |
| **決定の派生チェック**   | ラウンド終了時に、確定した各決定を適用範囲の調査済み事実（対象種別・画面ごとの差異など）と突き合わせ、検討されていなかった不整合・境界条件を候補に足す検査 |
| **再スキャン**（Step 5） | 聞ける質問が尽きたとき、更新後の spec.md 全体を読み直し、回答が新しく露出させた曖昧さから候補を作る                                                        |

### フロンティア

質問候補一覧のうち、未解決の前提が残っておらず**いまなら答えられる**質問の集合（設計ツリーを根側から確定させていく際の最前線のイメージ）。決定が確定するたびに、それに依存して聞けなかった候補が新しくフロンティアに入れるようになる。

未完了の事実調査または未確定の親論点に依存してフロンティアへ入れない候補を**ブロック候補**と呼ぶ。ブロック候補は質問候補一覧に残り、「候補が無い」とはみなさない。Step 5 へ進む前に、Step 3 の Step 5 進入ゲートで依存元までたどって解消・終端化する。

### ラウンド

フロンティアを 1 単位とする面談の進行単位。ラウンド内は 1 問ずつ順に問い、ラウンドが終わるたびにフロンティアを取り直す。

### カテゴリ

曖昧さスキャン（Step 1）とカバレッジ報告（Step 8）は、次の 10 カテゴリで論点を整理する。カテゴリは複数の論点を束ねる集約単位であり、状態を直接確定する最小単位ではない。本ファイルで「全カテゴリ」と書いたときはこの 10 個を指す。

- **機能スコープと挙動**: コアゴールと成功基準 / スコープ外宣言 / ロール・ペルソナの区別
- **ドメインとデータモデル**: エンティティ・属性・関連 / 一意性・識別ルール / ライフサイクル・状態遷移 / データ量の想定
- **インタラクションと UX フロー**: 主要ユーザージャーニー / エラー・空・ローディング状態 / アクセシビリティ・ローカライズ
- **非機能品質**: 性能 / スケーラビリティ / 信頼性・可用性 / 可観測性 / セキュリティ・プライバシー / コンプライアンス
- **連携と外部依存**: 外部サービス・API と障害モード / 入出力フォーマット / プロトコル・バージョン前提
- **エッジケースと失敗処理**: ネガティブシナリオ / レート制限 / 競合解決（同時編集等）
- **制約とトレードオフ**: 技術制約 / 明示的トレードオフ・棄却済み代替案
- **用語の一貫性**: 正準用語（プロジェクト文書・既存 spec・コード内の用語と照合）/ 避けるべき同義語
- **完了シグナル**: 受入条件のテスト可能性 / 測定可能な Definition of Done
- **その他**: TODO・未決マーカー / 定量化されていない曖昧形容詞（「堅牢」「直感的」等）

### 論点（decision point）と状態

状態はカテゴリではなく、カテゴリ内の個々の論点に付ける。上記カテゴリの各チェック項目（例: 性能、可観測性、セキュリティ）と、スキャンで新たに見つけた独立した決定事項をそれぞれ 1 論点として扱う。1 つの質問が複数の決定を含む場合も、状態は論点ごとに更新する。

| 状態            | 付ける場面                                            | 意味                                                                                                    |
| --------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Clear**       | Step 1 のスキャン                                     | 最初から十分に定義済みで質問は不要                                                                      |
| **Partial**     | Step 1 のスキャン中、または確定済み論点の再オープン中 | 記述・決定が不足しているか矛盾確認中。質問・調査の候補にする作業中状態                                  |
| **Missing**     | Step 1 のスキャン中                                   | 必要な記述が無い。質問・調査の候補にする作業中状態                                                      |
| **Resolved**    | 回答・調査事実の反映後、または親決定で非適用の確定後  | Partial / Missing だったが、spec への反映・検証または非適用理由の記録を終えて解消した                   |
| **Outstanding** | 質問にしないと決めたとき                              | Partial / Missing のままだが、実装・検証戦略に実質影響しない                                            |
| **Deferred**    | 質問・調査を保留、または中断したとき                  | plan 段階に委ねる、ユーザーが保留した、必要な事実を現時点で取得できない、または中断により意図的に未解消 |

Partial / Missing は作業中状態であり、終了時に残してはならない。終了条件は、**すべての論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定していること**とする。

### カテゴリ集約状態

カテゴリの表示用状態は、配下の全論点から機械的に集約する。集約状態で論点別状態を上書きしたり、隠したりしない。

1. 作業中は、Missing が 1 件以上なら `Missing`、それ以外で Partial が 1 件以上なら `Partial`。
2. 作業中状態が無く、Deferred が 1 件以上なら `Deferred`。
3. それ以外で Outstanding が 1 件以上なら `Outstanding`。
4. それ以外で Resolved が 1 件以上なら `Resolved`。
5. 全論点が最初から明確なら `Clear`。

例えば「非機能品質」で Performance が Resolved、Observability が Outstanding、Security が Deferred、残りが Clear なら、カテゴリ集約状態は Deferred とする。ただし Step 6 / Step 8 では Outstanding を含む論点別内訳も必ず併記する。

### カバレッジマップ

全論点の意味的同一性（カテゴリ・決定対象・適用範囲）、現在状態、確定結果または保留理由と、その論点が属するカテゴリの集約状態を対応付けた一覧。初回の曖昧さスキャン（Step 1）で作り、回答・調査事実の反映や状態変更のたびに更新する。Step 5 の再スキャンでも同じ一覧を維持し、作り直さない。設計ツリーと同じくセッション内部で維持し、ファイルには書き出さない。同じ論点について、設計ツリーのノード状態とカバレッジ状態は同じ処理内で更新する。ノードを作業中の未解決へ戻しながらカバレッジを Clear / Resolved / Outstanding / Deferred のまま残すことは禁止し、旧状態・旧確定値が必要なら現状態とは別の退避情報として保持する。終了条件は論点別状態で判定し、納得ゲート（Step 6）ではカテゴリ集約状態と Outstanding / Deferred の論点別サマリを提示し、完了報告（Step 8）では全カテゴリの集約状態と論点別内訳を出力する。

## 面談規律（全ラウンド共通）

- **共通理解に達するまで、あらゆる面を徹底的に面談する。** 表層の合意で切り上げない。
- **フロンティアはラウンド開始時に固定し、順に 1 問ずつ出す。** ラウンドの質問を一括提示せず、1 問提示して回答を待ち、反映してから次の 1 問を出す。ラウンドの全質問が済んでから次ラウンドへ進む。1 ラウンドの質問数に上限は設けない。ラウンド途中で質問を追加しない。
- **依存する質問は後のラウンドへ回す。** 同じラウンドでまだ解決していない質問に答えが左右される質問は、このラウンドに入れない。推測した前提の上に質問を積まない。前提となる質問が解決してから、次回以降のラウンドでフロンティアに入れる。
- **ラウンドが終わるたびに設計ツリーを再計算する。** ラウンド中の回答を設計ツリーに反映し、未解決の質問に依存していて聞けなかった質問候補のうち前提がすべて解決したものを、次のフロンティアへの追加候補にする。フロンティアの取り直しはラウンド終了処理（Step 3）で行い、ラウンド途中では行わない。
- **事実は聞かずに調べる。事実を見つけるのは常にこちらの仕事であり、ユーザーの仕事ではない。** コードベース・プロジェクト文書・既存 spec で確認できる事実は自分で調べ、質問から除外する。ユーザーに問うのは、通常のファイル検索（例: `rg`）・ファイル読み取り・シンボル／参照検索を尽くしても答えが出ず、ユーザーにしか決められない**決定**だけ。調査は自分で行い、サブエージェントには委譲しない。
- **調査待ちでラウンドを止めない。** 済んでいない調査は未確定の前提と同じ。今ラウンドに間に合わない調査があれば、それに依存する質問だけをフロンティアから外して質問候補一覧に戻し（調査が済んでから、次回以降のラウンドで改めてフロンティアに入れる）、フロンティアに残った質問は引き続き今ラウンドで出す。
- **選択肢を状況に応じて 1〜3 個、`A.` からのラベル付きで提示する。** 最適解が 1 つなら 1 個、実トレードオフがあるなら 2〜3 個。各選択肢に理由（1〜2 文）を添え、末尾に必ず自由入力の行を置く。ユーザーはラベル 1 文字だけで、推奨以外の選択肢も同じ手軽さで受諾できる。
- **`**推奨**` を付けたら必ず推奨理由を書く。** 最有力の選択肢を `**推奨**` 付きで `A` に置き、**なぜ他案よりそれを推すのか**（依拠した事実・既存実装・トレードオフの評価）を 1〜2 文で明記する。理由なしにマークだけ付けない。
- **自由記述はいつでも・どれだけ長くても可。** 選択肢外の回答・部分採用・条件付き回答（「A だが○○の場合は…」）を歓迎し、そのまま決定として扱う。
- **選択肢が選ばれても、掘り下げが必要なら次の選択肢セットを出す。** 選択の結果として新たな決定点・境界条件が生まれたら、質問候補一覧に足し、次回以降のラウンドでフロンティアに入れて納得まで掘り下げる。
- **上流の決定から先に確定させる。** 「スコープ」・「アクター」・「どのデータを正とするか」といった上流の決定は下流（画面挙動、エッジケース）を左右するので、序盤のラウンドのフロンティアは上流に寄る。
- **記録済みの決定との矛盾を検知したら、対象論点を再オープンして次ラウンドの先頭で確認する。** ユーザー回答・調査結果・再スキャンのいずれで見つけても、黙って spec を上書きせず、次を同じ処理内で行う。
  1. 対応する設計ツリーのノードを未解決へ戻す。
  2. カバレッジマップ上の同じ論点を Partial へ戻し、直前の状態と確定値は「保留中の旧確定値」として別に退避する。カテゴリ集約状態を直ちに再計算する。
  3. 「記録済みの決定との矛盾を検知したため、次ラウンドの先頭で確認します」と 1 行伝える。ユーザー回答が矛盾の発端なら、その回答は決着まで保留する。
  4. 旧決定を維持するか新しい内容へ変更するかを問う追撃質問を質問候補一覧に足し、次ラウンドの先頭候補にする。
  5. 決着まで対象論点を未解決の前提として扱い、それに依存するフロンティアの残り質問は質問候補一覧へ戻す。確認できる残りの質問だけ今ラウンドで出し切る。
  6. ユーザーの選択で決着した内容は Step 4A、調査事実だけで見かけの矛盾が解消した内容は Step 4B で反映・保存・検証する。その完了後に設計ツリーのノードを確定へ、カバレッジ状態を Resolved へ同時に変更し、退避した旧確定値を破棄してカテゴリ集約状態を再計算する。まだ曖昧なら Partial のまま追撃する。

- **回答が曖昧・矛盾なら追撃する。** 精密になるまで打ち切らない。境界を突くために仮想シナリオを作ってよいが、質問内で「仮定」と明示する。ユーザーが受諾するまではプロジェクトの事実・要件・決定として扱わず、spec にも反映しない。追撃質問は質問候補一覧に足し、次回以降のラウンドでフロンティアに入れて確認する。
- **先の質問を先出ししない。** 提示するのは現在の 1 問だけ。同一ラウンドの残りの質問も、将来のラウンドの質問を先に見せたり、並べて見せたりしない。
- **共通理解の確認が取れるまで、決定内容に基づいて動き出さない。** 反映先は spec.md だけで、plan・tasks・コードには着手しない。
- **ユーザーの中断シグナル（「stop」「ここまで」「一旦進めて」）は尊重する。** 新しい質問の提示を直ちに止めて「中断終了経路」へ移る。「終了」は質問ループの終了を意味し、チェックリスト・フック・完了報告を省略する意味ではない。

### 中断終了経路

spec の読み込み後にユーザーが中断を指示した場合は、面談のどの段階でも次を順に行う。

1. まだ受諾されていない回答は spec に反映しない。中断前に受諾・保存・検証済みの変更は維持する。
2. 現在の質問、未提示の候補、依存関係でブロックされた候補、未完了の事実調査、矛盾確認で再オープン中の論点を含め、残るすべての Partial / Missing 論点を Deferred へ変更する。理由を「ユーザーの中断」と記録し、対応する設計ツリーのノードを終端保留へ変更する。フロンティアと質問候補一覧を空にし、カテゴリ集約状態を再計算する。
3. すでに保存した spec に対して Step 4C の最終全体検証を行う。未解消内容を推測で補ったり、新しい Clarifications の Q&A を作ったりしない。
4. Step 5 の再スキャンと Step 6 の納得ゲートは省略し、Step 7 のチェックリスト再検証へ進む。
5. Step 7 の後、Extension hooks の規則どおり hooks.after_clarify を処理する。必須フックは実際に起動して完了を待ち、任意フックは案内を出す。
6. Step 8 の完了報告を「ユーザー中断による完了」として出す。中断時点、Deferred にした論点と理由、カバレッジ表、チェックリスト結果、フック処理結果、および plan へ進むか後で再実行するかの推奨を含める。

### 質問の形式

各質問は順に 1 問ずつ次の形式で出す。番号はラウンドごとに `Q1` から振り直す（ラウンドが変わったことが番号からも分かるようにする）。前ラウンドから持ち越した質問にも新しい番号を振り、提示時に持ち越しである旨を 1 行添える。

```text
❓ **Q1** - **<質問タイトル>**: <質問本文。前提の説明を含んでよく、複数段落でもよい>

➡️
- **A. <選択肢>** — **推奨**。<推奨理由 1〜2 文>
- **B. <選択肢>** — <理由 1〜2 文>
- **C. <選択肢>** — <理由 1〜2 文>
- **自由入力** — 上記以外・部分採用・条件付き回答（分量無制限）
```

選択肢の数は 1〜3 個で状況に応じて増減し、`**自由入力**` の行は常に置く。回答は提示中の 1 問に返す — 「A」「B」などラベル 1 文字、「推奨で」「はい」、または自由記述のいずれでもよい。「スキップ」「保留」で飛ばすと、その質問は次ラウンドへ持ち越す（番号は持ち越し先のラウンドで振り直す）。提示中の質問以外に触れる自由記述（後続質問への先行回答、確定済み決定の明示的な修正）もそのまま決定として受け付け、提示中の質問の回答と同様に Step 4A で 1 件ずつ反映する（フロンティアの取り直しはラウンド終了時）。番号はラウンド内の参照用で、spec.md には記録しない（Clarifications の形式は Step 4A のとおり）。過去のラウンドの質問に触れるときは「ラウンド n の Qk（<質問タイトルまたは要旨>）」の形で参照する — 番号だけでは思い出せないので、質問内容の再掲を必ず添える。

## Workflow

### Step 1. 曖昧さスキャン

spec.md 全体を読み、「用語集」の全カテゴリ内にある各論点について **Clear / Partial / Missing** を判定した内部カバレッジマップを作る。これは初回スキャン時だけの初期化である。Step 5 から再実行するときはマップを作り直したり全論点をこの 3 状態へ戻したりせず、Step 5 の状態照合規則に従う。カテゴリに直接 1 状態を付けるのではなく、論点別状態からカテゴリ集約状態を算出する。

Partial / Missing の各論点から質問候補を作り、**質問候補一覧**にまとめる。除外するのは「実装・検証戦略に実質影響しない」「plan 段階に委ねるのが適切（内部メモに残す）」ものだけ（事実で答えが決まるものは Step 2 で調べて落とす）。**質問数の上限は設けない。**

除外した各論点は Partial / Missing のまま残さず、カバレッジマップ上で **Outstanding** または **Deferred**（「用語集」の状態定義に従う）へその場で変更する。変更後にカテゴリ集約状態を再計算する。論点の状態を確定しないと Step 5 の終了条件に到達しない。

### Step 2. 事実ゲートとフロンティアの算出

質問候補一覧へ候補が追加されるたび、フロンティアを算出する前に、まだ事実ゲートを通過していない候補、および依存元の確定などで前提が変わった候補すべてへ、次の順序で**事実ゲート**を適用する。初回の Step 1 で作った候補だけでなく、追撃・掘り下げ・決定の派生チェック・再スキャンで追加された候補も対象にする。

1. 候補の答えを「調査で確定できる事実」か「ユーザーが方針として確定すべき決定」かに分類する。
2. 事実候補は、コードベース・プロジェクト文書・既存 spec を自分で調べる。答えが確定した候補は質問候補一覧から落とす。調べた事実で spec の曖昧な記述が解消するなら **Step 4B** で spec 本体だけを直し、反映・検証後に対応論点を Resolved へ変更する。Clarifications には追記しない。
3. 事実調査が未解決の決定に依存する候補、または今ラウンド中に調査が完了しない候補は、質問候補一覧に「調査待ち」として残す。依存元の確定または調査の完了後に事実ゲートを再適用し、それまではフロンティアへ入れず、ユーザーへの質問にも変換しない。
4. 調査可能な情報源を尽くしても事実として確定できず、プロジェクトの方針・要件を新たに選ぶ必要があると分かった候補だけを決定候補へ分類し直す。外部に正解が存在する事実を単に取得できないだけなら決定扱いせず、実装・検証戦略への影響がない場合は Outstanding、それ以外は調査不能の理由を記録して Deferred にする。

事実ゲートを通過して決定候補として残った各候補へ、Step 1 と同じ質問化の影響度基準を再適用する。回答がどう決まっても実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれも変わらない候補は、質問候補一覧から外す。外した候補が対応していた論点は Outstanding / Deferred のいずれかへ変更し、カテゴリ集約状態を再計算する。

残った決定候補を、その質問が確定させる設計ツリーのノードと紐付ける。そのうち**未解決の前提が残っていない候補**を質問候補一覧から取り出し、フロンティアに加える（フロンティアに入らなかった候補は質問候補一覧に残る）。フロンティアに加えた候補を (影響度 × 不確実性) 順に並べ、「質問の形式」の規則で番号を振る。

### Step 3. ラウンドループ

現在のフロンティアを 1 つのラウンドとし、ラウンド内は 1 問 1 答で進める:

1. ラウンド開始時に「ラウンド n（m 問）」を 1 行で宣言する。前ラウンドで検知した矛盾の確認から始まるラウンドでは、その旨を宣言に含める（例: 「ラウンド n（m 問）— 記録済みの決定との矛盾の確認から始めます」）。質問の一覧は先出ししない。
2. 「質問の形式」に従い、まずはラウンドの先頭 1 問だけを提示してユーザーの回答を待つ（提示順は Step 2 の並び順。番号はこの順に Q1 から振ってあるため、昇順に進む）。
3. 回答が返ったら、確定した内容を Step 4A の手順で反映・保存し、対応論点を Resolved へ変更してから次の 1 問を提示する。曖昧・矛盾のまま残った回答は追撃質問を作って質問候補一覧に足し、次回以降のラウンドでフロンティアに入れて確認する（今ラウンドには差し込まない）。保留にした旨と理由を 1 行伝えてから次の 1 問へ進む。スキップ・保留された質問は次回以降のラウンドへ持ち越す（番号は持ち越し先で振り直す）。回答が記録済みの決定と矛盾する場合は、「記録済みの決定との矛盾を検知したら」の規律に従って保留し、確認の追撃質問を次ラウンドの先頭で出す。
4. 既出の回答がラウンド内の後続質問を確定していたら、その質問は提示せず、「既存の回答で確定したため回答済みとして反映した」と 1 行で伝える。後続質問の前提自体を成立しなくしていたら、「設計ツリー」の非適用規則を直ちに適用し、対応論点を Resolved へ変更してから「親決定により非適用になった」と 1 行で伝える。
5. ラウンドの質問が尽きたら**ラウンド終了処理**を行う: 「ラウンド n 完了 — 確定 x 件・持ち越し y 件」を 1 行で報告し、**決定の派生チェック**を行ってから、設計ツリーを再計算して Step 2 へ戻り、次のフロンティアを取り直す。派生チェックでは、このラウンドで確定した各決定を適用範囲の調査済み事実（対象種別・画面ごとの差異、一覧/詳細/履歴、項目構成、必須/任意など）と突き合わせ、決定が検討していなかった不整合・境界条件を質問候補一覧に足す。

ラウンド終了後（初回の Step 2 でフロンティアが空だった場合も同じ）は、次の **Step 5 進入ゲート**を上から順に評価する。

1. フロンティアに候補があれば、Step 3 の次ラウンドへ進む。
2. 未完了の事実調査があれば、他の聞ける質問を妨げない範囲で調査を完了し、結果に Step 2 の事実ゲートを再適用する。調査不能なら Step 2 の規則どおり Outstanding / Deferred へ終端化する。Step 5 へは進まない。
3. 未確定の親論点に依存するブロック候補があれば、各候補から依存元を根側へたどり、次のように処理して Step 2 へ戻る。Step 5 へは進まない。
   - 作業中の親論点に対応する候補が質問候補一覧に無ければ、その Partial / Missing 論点から親候補を復元する。
   - 親論点が Clear / Resolved なのに子がブロックされたままなら適用条件を再評価し、適用される子を次のフロンティア候補にし、適用されない子には「設計ツリー」の非適用規則を適用する。
   - 親論点が Deferred なら、親の決着なしに確定できない子孫も理由付き Deferred として終端保留にする。親論点が Outstanding なのに実装・検証戦略へ影響する子孫があるなら、親を Partial へ再オープンして候補を復元する。子孫にも実質影響が無ければ Outstanding として終端保留にする。
   - 自己依存または循環依存を検出したら、依存グラフの誤りとして枝を組み直す。調査事実だけで順序を決められなければ、最も上流の決定を依存の無い根候補として置き直す。循環を残したまま再スキャンしない。
   - 状態変更後に設計ツリーとカテゴリ集約状態を再計算する。
4. **質問候補一覧が空で、未完了の事実調査もブロック候補も無く、すべての論点が Clear / Resolved / Outstanding / Deferred のいずれかである場合だけ** Step 5 へ進む。条件を満たさないのに進行可能な候補を復元できない場合は、残る作業中論点を理由付き Deferred として終端化してから、このゲートを再評価する。

### Step 4. 反映手順: spec.md への即時反映

Step 3 の次に実行する工程ではない。ユーザー回答が確定するたびに Step 3 から Step 4A を呼び、調査事実で曖昧さが解消するたびに Step 2 から Step 4B を呼ぶ。両経路を混ぜない。

#### Step 4A. ユーザー回答の反映

1. 初回のみ: spec.md の `## Clarifications` セクション（無ければ spec.md の概要セクション直後に作成）配下に `### Session YYYY-MM-DD` を用意する。
2. 受諾した回答ごとに `- Q: <質問> → A: <確定回答>` を 1 行追記する。
3. 確定した決定を「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。
4. 1 回の回答に複数の決定が含まれる場合も、決定を 1 件ずつ反映・保存・検証する。Clarifications の Q/A 行は受諾回答につき 1 行のままとし、同じ回答を重複記録しない。
5. 各決定の保存・検証が成功した後、その論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

#### Step 4B. 調査で確定した事実の反映

1. spec.md の `## Clarifications` / `### Session YYYY-MM-DD` を新設せず、Q/A 行も追記しない。Clarifications はユーザーとの質疑だけを記録する。
2. コードベース・プロジェクト文書・既存 spec から確認できた事実だけを、「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。推測や仮想シナリオは事実として反映しない。
3. 確認した事実を 1 件ずつ反映・保存・検証する。
4. 保存・検証が成功した後、その事実で解消した論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

#### Step 4C. 共通の反映・検証規則

1. 内容を最適なセクションへ反映する:
   - 機能の曖昧さ → Functional Requirements
   - アクター・操作の区別 → User Stories / Actors
   - データ形状 → Data Model（順序を保ち、制約は簡潔に）
   - 非機能 → Success Criteria の測定可能な形（曖昧形容詞は指標へ変換）
   - エッジケース → Edge Cases / Error Handling
   - 用語 → spec 全体で正準用語に正規化（必要なら `（旧称 "X"）` を一度だけ）
2. 新しい内容が過去の曖昧な記述を無効化するなら、重複追記ではなく**置換**する。矛盾する古い記述を残さない。
3. **反映のたびに spec.md を保存する。** 無関係なセクションの並び・見出し階層は変えない。追記は最小限かつテスト可能な形に保つ。
4. **保存のたびに検証する**（最終ラウンド後にも全体パスを 1 回）:
   - Step 4A では Clarifications の Session 配下が受諾回答 1 件につき 1 行で重複していない。Step 4B では Clarifications に差分が無い
   - 反映内容が解消するはずだった曖昧な記述・プレースホルダが残っていない
   - 無効化された選択肢・矛盾する古い記述が残っていない
   - Markdown 構造が正しい（新設見出しは Step 4A の `## Clarifications` / `### Session YYYY-MM-DD` のみ）
   - 更新した全セクションで正準用語が一貫している

### Step 5. 再スキャンループ

Step 3 の Step 5 進入ゲートを通過した場合だけ、**更新後の spec.md に対して Step 1 の検出スキャンをやり直す**（回答が新しい曖昧さ・派生論点を露出させるため）。再スキャンは**初回実行と同じ厳しさで、更新後の spec を初見のつもりで**行うが、論点状態は初期化せず、次の順序で既存カバレッジマップへ差分統合する。

1. 再スキャン前の各論点について、意味的同一性・現在状態・確定結果または保留理由・依存関係を保持する。
2. 検出した論点を意味的同一性で既存論点と照合する。既存論点は別表現でも同じ決定対象と適用範囲なら同一とみなし、新規論点として作り直さない。
3. 既存の Clear / Resolved / Outstanding / Deferred 論点は、更新後の spec が記録済みの結果を支持し、新しい適用範囲・境界条件・矛盾が無い限り、状態と根拠をそのまま維持する。新しい矛盾などが見つかった場合も確定状態を黙って上書きせず、「記録済みの決定との矛盾を検知したら」の確認フローへ渡す。
4. 既存論点に対応しない本当に新しい論点だけを Clear / Partial / Missing へ分類し、新規の Partial / Missing から質問候補を作る。既存論点が本文から見つからない場合も自動削除せず、親決定による非適用なら「設計ツリー」の非適用規則、それ以外なら矛盾候補として扱う。
5. 差分統合後にカテゴリ集約状態を再計算する。

合格基準は「直後にこのスキルを再実行しても、決定を変え得る新しい質問が出ない」状態。新たな Partial / Missing の論点が見つかれば質問候補一覧に候補が補充され、聞ける質問が再び生まれるので、Step 2〜4 の新ラウンドへ。再スキャンで聞ける新しい質問が生まれず、全論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定するまで繰り返す。

ただし、再スキャンのたびに軽微な論点から新しい質問が生まれ続けて、面談がいつまでも終わらなくなる事態は避ける。検出の厳しさは保ったまま、**質問化の閾値を段階的に上げる**。

再スキャンで生成した候補は意味的重複を検査する。過去に Resolved / Outstanding / Deferred へ確定した論点と意味的に同一で、回答が同じ決定結果に収束し、新しい適用範囲・境界条件・矛盾も無いなら、新規候補として追加しない。表現が異なるだけの言い換えも重複とみなす。

> **※ 閾値の定義** — 「候補を質問として出すために、回答が何を変え得る必要があるか」の基準。次の 2 段階を使う。
>
> - **初回スキャン〜1 回目の再スキャン** — Step 2 の関門と同じ基準。回答次第で実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれかが変わる論点を質問にする。
> - **2 回目以降の再スキャン** — 回答次第で決定や実装の分岐が変わる（どの選択肢を選ぶかで別の設計・実装になる）論点だけを質問にする。この基準に届かない軽微な論点（表現の細部、どう答えても同じ実装に落ちる明確化など）は Outstanding として状態を確定し、Step 6 の納得ゲートで一覧提示する（ユーザーは選択肢 2 で再オープンできる）。

### Step 6. 納得ゲート

全論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定したら、カテゴリ集約状態、Outstanding / Deferred の論点別サマリ、今回変更したセクション一覧を提示し、**AskUserQuestion 等の対話UIで選択肢を出して納得を確認する**。（対話 UI を利用できない場合は、同じ 3 つの選択肢を通常の応答本文に提示し、ユーザーの選択を待つ。）自由入力の「OK」待ちにしない — **この納得ゲートでは**確認の形式を毎回これで固定する（Step 3 のラウンドには適用しない。そちらは面談規律の質問形式どおり本文テキストで提示する）。

選択肢は次の 3 つで固定し、推奨には理由を添える:

1. **完了して次へ進む** — `**推奨**`（推奨理由: 全論点の状態が確定しており、未解決の質問が残っていないため）
2. **追加で掘り下げたい領域がある** — 領域と具体的な懸念を聞き取り、該当論点（必要なら新しい論点）を Partial にして質問候補一覧へ足し、Step 2 へ戻る
3. **気になる領域は残るが、ここで打ち切る** — 領域と具体的な論点を聞き取り、「中断終了経路」の 2 以降に従って、その各論点を Deferred として記録したうえで Step 7 以降の後処理へ

1 が選ばれたら Step 7 へ進む。

2 が選ばれたら、掘り下げたい領域と気になっている内容を自由記述で答えてもらう確認質問を出し、回答の内容を確かめてから上記 2 の処理（該当論点を Partial にして質問候補一覧へ足し、カテゴリ集約状態を再計算して Step 2 へ戻る）に入る。

選択肢外の自由記述（追加論点の直接指摘など）が返ってきた場合も受け付け、内容に応じて 2 または 3 と同じ扱いにする。

### Step 7. チェックリスト再検証

`FEATURE_DIR/checklists/requirements.md` があれば（無ければ黙ってスキップ）:

1. コードフェンス外のチェックボックス行（`- [ ]` / `- [x]` / `- [X]`、ネストのインデント許容）だけを対象に、現在の状態と項目テキストを before スナップショットとして記録する。
2. 各項目を**更新後の spec** に対して再評価し、状態が変わる項目だけ `[ ]`/`[x]` を切り替えて保存する。見出し・メタデータ・注記・行順・空白など他は一切変更しない（差分ノイズを出さない）。
3. before との比較で 3 リストを作る: **新規通過**（unchecked → checked）/ **退行**（checked → unchecked）/ **未通過のまま**。before/after の通過数（例: 12/16 → 15/16）も記録する。

### Step 8. 完了報告

（after_clarify フックの処理を済ませてから）以下を報告する:

- 終了種別（通常完了 / ユーザー中断）。中断の場合は中断時点と、中断後の質問・回答を反映していないこと
- ラウンド数と総質問数（ラウンドごとの内訳を添えてよい。質問→回答の一覧は Clarifications 参照でよい）
- 更新した spec のパスと触れたセクション一覧
- チェックリストの before/after 通過数、新規通過・退行した項目、未通過のまま残った項目（要注意領域として列挙）
- カバレッジ表 — 全カテゴリの集約状態を **Resolved** / **Clear** / **Deferred** / **Outstanding** のいずれかで示し、カテゴリごとに論点別状態の内訳を併記する。Partial / Missing の論点が 1 件でも残っているなら完了報告へ進まない
- Outstanding / Deferred が残る場合は、`/speckit-plan` に進むか後で再実行するかの推奨
- 次コマンドの提案（通常は `/speckit-plan`）

## Behavior rules

- このワークフローは `/speckit-plan` の**前に**完了している想定。ユーザーが明示的にスキップして先へ進む場合は、下流での手戻りリスクが上がることを警告した上で従う。
- 有意な曖昧さが無ければ「クリティカルな曖昧さは検出されませんでした」と報告し、全論点が Clear であるカテゴリ集約サマリを出して Step 6 の納得ゲートへ進む（無理に質問を作らない）。
- 機能の明確化をブロックしない限り、技術スタックの推測質問はしない。
- このスキルが変更してよいのは spec.md と `checklists/requirements.md`（Step 7 のチェックボックス更新のみ）だけ。plan / tasks / コード など他のファイルは変更しない。
