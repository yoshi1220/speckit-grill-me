# SpecKit Grill With Docs

**必須**: 先に `../speckit-grill-me/SKILL.md` を最後まで読み、その手順に従う。

同じ親ディレクトリにある `speckit-grill-me` を**ベーススキルとして**実行する。言語設定、前提、Extension hooks、用語集、面談規律、中断終了経路、Workflow Step 1〜8、Behavior rules、成果物、終了条件はすべてベースのとおりとする。

本ファイルで使う論点、論点状態、質問候補一覧、フロンティア、ラウンド、設計ツリー、カバレッジマップ、依頼マップ、中核決定と派生決定、帰結による確定、根拠のある要素とエージェントが追加した要素もベースの定義に従う。

本スキルが追加する責務は 1 点だけである。**面談中に確定した正準用語と、記録条件を満たすプロジェクト横断の業務ドメイン・技術構成の決定を、その場で通常の Markdown 文書へ永続化する。** Serena および `.serena/` は使用せず、利用可能であることも前提にしない。

ベースの Behavior rules にある「変更してよいのは spec.md と `checklists/requirements.md` だけ」は、本スキルでは後述のドメイン知識文書を加えた範囲に読み替える。plan、tasks、コード、設定ファイルを変更しない点は変わらない。

## ベースの明確化規則の適用

- 設計ツリー、カバレッジマップ、依頼マップはセッション内だけで維持する。掘り下げる前に、すべての目標の 6 つの中核観点を確認する。ドメインの質問にも、ベースの事実ゲート、依存順序、固定ラウンド、根拠提示、深さ制限、段階別閾値を適用する。知識の記録欄を埋める必要があることを、質問の根拠にしない。
- 番号付き要件、出典付きの確認済みの前提、決定から導く受入シナリオ、「対象外と制限事項」の未決事項は `FEATURE_SPEC` に残す。知識の成果物を、これらの記録や目標別カバレッジ、計画へ進めるかの確認の代わりにしない。

  Clarifications は受諾回答につき 1 行とし、調査事実・帰結の Q/A を追加しない。同じ要件を変える決定や相互に依存する決定は、ベース Step 4A の例外に従って spec へ 1 回の保存で反映する。受諾回答と矛盾する中間状態を保存しない。独立した知識項目は個別に処理する。
- 帰結で確定した要件は、新しいユーザー方針を決めたものでも、未知の事実を確認したものでもない。spec に元の受諾済み決定と調査済み事実を引用し、既存規則を適用しただけで新たな決定記録を作らない。

  ベース Step 6 の納得ゲートでユーザーが帰結を受諾するまでは、必須の記録先は spec だけとする。この段階では、知識の更新を待たずに、その論点を Resolved にしてよい。

  受諾後は、記録対象となるプロジェクト横断の用語・規則を、同じ出典とともに永続化する。対象成果物をすべて検証してから Step 7 へ進む。決定記録の記録条件は維持し、受諾だけで新しいトレードオフがあったとはみなさない。
- Outstanding / Deferred の論点、気づいたが質問しなかった状況、未確認の仮定、未受諾の仮想シナリオを、確定済みのドメイン知識にしない。ベースの規則に従って spec とカバレッジ報告へ残す。合意済み拡張は受諾された範囲とともに記録し、計画で扱うことにした内部詳細を、知識として確定した決定に変えない。
- 中断時は、保存済み spec の帰結を維持し、完了報告で納得ゲート未確認と明示する。受諾なしに正準知識へ昇格させない。受諾・保存・検証済みの知識変更は維持する。永続化に失敗した場合は、「永続化失敗時の扱い」に従う。

## ドキュメントの所在と初期化

適用される上位の実行指示と constitution に従い、それらを上書きしない。その制約の範囲内で、正準保存先を次の優先順位で決める。

1. このセッションでユーザーが明示した保存先
2. 対象パスに適用される `AGENTS.md`、`CLAUDE.md` 等のエージェント向け指示で明示された保存先
3. README、CONTEXT、文書規約等のプロジェクト文書で正準と明示された保存先
4. 標準の `docs/domain_knowledge/`

同じ優先順位の指示が競合する場合は、対象 feature または保存対象に、より具体的に適用される指示を優先する。それでも一意に決められなければ推測して作成せず、競合する候補と根拠を示してユーザーに確認する。

正準保存先を解決したら、セッション中で使う次の論理パス名を確定する。これらは本ワークフロー内のラベルであり、シェル環境変数ではない。

- `KNOWLEDGE_ROOT`：解決した正準知識ディレクトリ。優先された指示がコンテキストファイルを指定している場合は、その親ディレクトリとする。
- `CONTEXT_FILE`：優先された指示または既存のプロジェクト規約が明示する入口ファイル。指定がなければ `<KNOWLEDGE_ROOT>/CONTEXT.md` とする。優先された指示がコンテキストファイルを指定している場合は、そのファイルを直接使う。
- `ADR_DIR`：優先された指示または `KNOWLEDGE_ROOT` 配下の既存プロジェクト規約が定める ADR ディレクトリ。指定がなければ `<KNOWLEDGE_ROOT>/adr/` とする。

書き込み前にこれらを 1 回だけ解決し、セッションを通して同じ値を使う。既存規約から複数の入口ファイルまたは ADR ディレクトリが候補となり、優先順位の規則でも一意に選べない場合は、複数箇所へ書かずユーザーへ確認する。

別の正準保存先が指定されていなければ、次を標準とする。

```text
docs/domain_knowledge/
├── CONTEXT.md
├── <domain-topic>.md
└── adr/
    └── 0001-<decision-name>.md
```

- `CONTEXT_FILE` を知識ベースの正準な入口とする。プロジェクト固有の正準用語、概念の意味と境界、避ける同義語を簡潔に記録する。実装詳細、feature 仕様、作業メモ、技術選定の経緯は置かない。
- 既存の `CONTEXT_FILE` があれば、その構造と記述言語を保って該当箇所だけを更新する。
- `KNOWLEDGE_ROOT` または `CONTEXT_FILE` が存在しない場合は、最初に記録対象が確定した時点で作成する。空の知識ベースを事前に作る必要はない。
- 新しい `CONTEXT_FILE` は、プロジェクトの文書言語に合わせ、少なくとも「文書タイトル」「正準用語と主要概念」「ドメイン境界」「関連ドキュメント」に相当する節を持つ。見出し表記は既存プロジェクトの文書言語と見出し規約に合わせる。用語の定義は 1〜2 文に収め、「何をするか」より「何であるか」を定義する。
- 同じ概念に複数の言い方があれば 1 つを正準用語に選び、`_Avoid_: <避ける同義語>` の形で記録する。一般的なプログラミング用語は追加せず、このプロジェクトのドメインに固有の概念だけを扱う。
- `CONTEXT_FILE` の用語集だけでは境界・業務ルールを正確に保守できない場合だけ、`<KNOWLEDGE_ROOT>/<kebab-case-domain-topic>.md` を作成する。独立文書を作るのは、1 つの概念群について複数の境界、不変条件、業務ルールを説明する必要があり、`CONTEXT_FILE` の 1〜2 文の定義では意味を損なう場合に限る。判断に迷う場合は `CONTEXT_FILE` に留め、ファイルを分けること自体を目的にしない。
- 個別文書を作成したら、`CONTEXT_FILE` の関連ドキュメント一覧へ相対リンクと一文の説明を追加する。リンク切れ、存在しない根拠、推測したパスを書かない。
- 記録条件を満たす決定は `<ADR_DIR>/NNNN-<kebab-case-decision>.md` へ書く。`ADR_DIR` は最初の ADR が必要になった時点で作成する。
- `KNOWLEDGE_ROOT` 内に別の構造や命名規約があれば、それを維持する。無関係な文書の移動・改名・再編は行わない。

ベースの「前提」4 では、通常の調査資料に加えて `CONTEXT_FILE` を必ず読み、対象 feature に関係する `KNOWLEDGE_ROOT` 内の文書も読む。`CONTEXT_FILE` がまだ存在しない場合は、他の関連文書を調査してから、上記の作成条件に従う。

読み書きには通常のファイル検索・読み取り・編集機能を使う。書き込みのたびに対象ファイルを読み戻す。確定内容の正準な定義または決定記録が、意図した成果物内に 1 つだけ存在し、別の正準記録として複製されていないことを確認する。正準記録へのリンクや定義済み用語の使用など、通常の参照は重複に数えない。既存構造、Markdown、相対リンクを壊していないことも確認する。

正準保存先を読めない、作れない、更新できない、または検証できない場合は、別の場所へフォールバックせず、失敗内容を報告して停止する。

## 情報源の権威

内容の種類ごとに、次の情報源を正とする。

| 内容 | 正とする情報源 |
| --- | --- |
| プロジェクト原則 | 存在する場合の `.specify/memory/constitution.md`。他の要件・決定に対する上位制約 |
| feature 固有の要件・期待挙動 | 現在の `FEATURE_SPEC` と、このセッションでユーザーが明示的に確定した決定 |
| feature を超える用語・ドメイン知識・設計判断 | 正準の `CONTEXT_FILE`、`KNOWLEDGE_ROOT` 内のドメイン別文書、`ADR_DIR` 内の ADR。ただし、このセッションでユーザーが変更を明示的に確定し、保存・検証を完了した場合は新しい決定 |
| 現在の実装状態 | 実コード、スキーマ、migration、model、interface、test 等の一次情報 |

- constitution に反する回答は確定扱いにせず、対象論点を再オープンして適合する決定を確認する。constitution 自体の変更は本スキルの範囲外とする。
- ユーザーが矛盾を理解した上で決定を維持する場合、その論点を理由付き Deferred にする。constitution に反する内容を spec またはドメイン知識文書へ確定事項として書かない。
- ユーザーの新しい回答は、提案中、曖昧、矛盾確認中の段階では既存文書を上書きする権威を持たない。ベースの矛盾確認規律を通り、spec と必要な知識文書の保存・検証が完了して初めて新しい決定を正とする。
- 現在の実装事実を、そのまま望ましい要件や設計判断とはみなさない。情報源が食い違う場合は黙って優先・上書きせず、ベースの矛盾確認規律に従う。

## spec とドメイン知識文書の書き分け

| 内容 | 書き込み先 |
| --- | --- |
| この feature 固有の要件、挙動、エッジケース、受入条件 | `FEATURE_SPEC`。ベースの Step 4A / 4B / 4C に従う |
| feature を超えて通用する正準用語、概念、境界 | `CONTEXT_FILE`、またはそこから参照する `KNOWLEDGE_ROOT` 内のドメイン別文書 |
| 将来も参照すべき業務ドメイン・技術構成の決定 | `ADR_DIR`。ただし、次の記録条件 3 つをすべて満たす場合だけ |

決定の記録条件は、①覆すコストが実質的に高い、②判断の背景を知らない将来の読者には、その決定が意外に見える、③実際に代替案があり、理由をもって選んだ、の 3 つとする。1 つでも満たさなければ ADR は作成しない。

- 同じ内容を spec とドメイン知識文書の両方で正準定義として管理しない。feature を超える定義は知識文書を正とし、spec には feature の理解・検証に必要な最小限の文脈と feature 固有の帰結だけを書く。Clarifications の Q/A 行は監査記録なので二重管理には数えず、省略しない。
- 同一の確定事項が用語・ドメイン知識と ADR の両方に関係する場合、知識文書には現在の意味、境界、業務ルールだけを、ADR には採用理由、代替案、トレードオフだけを記録する。同じ説明を正準情報として複製しない。必要なら相対リンクで関係を示す。
- `CONTEXT_FILE` は短く断定的な用語集とドメイン境界の入口として保つ。実装詳細、仕様、スクラッチパッド、ADR の本文を混ぜない。詳細が独立したドメイン主題になる場合は個別文書へ移し、`CONTEXT_FILE` には短い要旨とリンクだけを置く。
- 新規のドメイン別文書には、短く安定したタイトル、冒頭の要約一文、概念と業務ルールの境界を記載する。一次情報が存在する場合は、確認できた相対パスも記載する。ユーザーが確定した業務方針には実装上の根拠を必須とせず、存在しない証拠を作らない。設計判断の経緯は ADR へ分ける。該当しない節を埋めるために推測しない。
- 新規 ADR は `ADR_DIR` 内の既存番号の最大値に 1 を足した 4 桁の番号を使う。タイトルと、文脈・決定・理由をまとめた 1〜3 文を必須とする。Status、検討案、結果・影響の節は実際に価値がある場合だけ追加し、テンプレートを埋めることを目的にしない。
- 既存 ADR を覆す場合は、古い ADR を消さず、新しい ADR を作成して旧 ADR の Status を `superseded by ADR-NNNN` へ更新する。
- 確定した内容は 1 件ずつ即時保存する。1 回の回答で独立した複数の用語・決定が確定した場合もまとめ書きせず、1 件ずつ処理する。

  1 件の確定事項から複数種類の更新が必要な場合は、① spec、② `CONTEXT_FILE` の用語・概念、③ `KNOWLEDGE_ROOT` 内のドメイン別文書、④ `CONTEXT_FILE` の関連文書索引、⑤ `ADR_DIR` 内の新しい ADR、⑥ `ADR_DIR` 内の supersede 対象の旧 ADR、⑦全対象の読み戻し検証、の順で処理する。不要な成果物の手順は飛ばす。

  各書き込み直後に個別に検証し、⑦では成果物間の整合性もまとめて検証する。すべて成功してから、その論点を Resolved にする。
- Step 4A の 1 件が知識文書への記録対象でもある場合は、spec の保存・検証後、知識文書の保存・読み戻し検証を完了してから論点を Resolved にする。
- Step 4B で確認した実装事実だけを、業務ドメインまたは技術構成の「決定」へ昇格させない。プロジェクト横断の判断として記録する必要があれば、ユーザーが決める論点として質問候補一覧へ追加し、受諾後にだけ書く。

## 文書の更新規律

- 既存文書を更新するときは、その文書の構造、文体、用語、リンク形式を維持し、確定事項に関係する最小範囲だけを変更する。
- 用語の記録には、概念の意味と境界、正準表記、避けるべき同義語を含める。実装詳細や feature 固有の作業メモを用語定義へ混ぜない。
- ADR には、決定内容、適用範囲、選択理由を含め、重要な棄却案は将来の再検討に価値がある場合だけ残す。存在しない経緯や代替案を補わない。
- 新規のドメイン別文書を作成した場合は、`CONTEXT_FILE` の索引更新までを同じ記録処理として扱う。文書だけ、または索引だけが更新された状態では完了とみなさない。ADR は `CONTEXT_FILE` へリンクすることを必須としない。
- 正準用語やドメインルールを変更する場合は、単純に併記して矛盾を残さず、現在の内容が一意に分かるよう既存の定義を置換する。設計判断の変更は ADR の superseded 規則に従う。

## 永続化失敗時の扱い

spec と知識文書への反映は単一トランザクションではない。次のいずれかの組で、一方の保存または検証に失敗した場合は、対象論点に補助状態「永続化未完了」を付けて停止する。

- spec と知識文書
- ドメイン別文書と `CONTEXT_FILE` 索引
- supersede する新旧 ADR

「永続化未完了」は永続化の進捗を示す補助状態であり、ベースの論点状態ではない。帰結の受諾後の更新などで論点がすでに Resolved の場合は、確定値を別に退避し、設計ツリーのノードとカバレッジ状態を同じ処理で Partial に戻す。設計ツリーとカバレッジマップ上の状態は Partial のまま維持し、必要な全ファイルの保存・検証が完了するまで Resolved にしない。

- 停止時に、対象論点、確定内容、保存・検証済みのファイル、未反映または未検証のファイル、失敗内容、次に必要な復旧操作を明示する。
- 再開時は、新しい質問の前に未完了の保存・検証を終える。保存済みのファイルも読み直し、重複や新しい矛盾がないことを確認する。
- 新しいセッションでは、最新の Clarifications と関連知識文書を照合する。未反映内容を一意に再構成できれば該当ファイルへ反映し、できなければ推測せずユーザーへ確認する。
- 永続化未完了が残る間は、新しい質問、再スキャン、納得ゲート、通常の完了報告へ進まない。ユーザーが中断を求めた場合も、通常の中断完了ではなく復旧情報を報告して停止する。

## セッション中の追加規律

- **正準用語と衝突したら最初の機会に指摘する。** 質問作成時でも回答で見つかった場合でも、ベースの矛盾確認規律に従う。対象論点を再オープンし、旧確定値を退避し、矛盾を伝え、1 つの決定を問う確認を次ラウンドの先頭に置く。別のドメイン決定と抱き合わせたり、固定済みの現フロンティアへ挿入したりしない。
- **曖昧・多義的な語は正準用語へ確定させる。** どの概念を指すか確認し、意味と境界が確定したら spec の表記を正規化し、必要なら知識文書を即時更新する。
- **概念の境界は具体的なシナリオで確認する。** 仮想シナリオであることを明示し、受諾前の内容は事実・決定として保存しない。
- **コードと突き合わせる。** ユーザーの説明、知識文書、実装が食い違えば、実装状態の一次情報を示した上で確認する。要件や正準文書を黙って実装へ合わせない。
- **記録済み文書と矛盾する回答・調査結果は、ベースの矛盾確認規律で扱う。** 変更が確定した場合だけ関連文書を更新し、保存・検証後に論点を Resolved にする。
- **中断終了経路では、確定・保存・検証済みの文書変更を維持し、未受諾の内容は書かない。** 更新した知識文書は完了報告へ含める。

## 完了報告への追記

ベースの Step 8 完了報告に次を加える。

- 解決して使用した `KNOWLEDGE_ROOT`、`CONTEXT_FILE`、`ADR_DIR` のパス
- 作成・更新した文書のパスと、その区分（コンテキスト入口 / ドメイン別文書 / ADR）
- 追加・変更した用語、概念、決定の要旨
- 記録済み内容との矛盾を明示して解消または保留した論点
- 納得ゲートで受諾され、知識へ反映した帰結と、その元の決定・事実。中断により未確認のまま残った帰結は区別する
