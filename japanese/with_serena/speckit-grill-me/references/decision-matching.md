# カテゴリをまたぐ論点の照合

カバレッジマップの論点ごとに、セッションを通じて同じ ID を使う。スキャンや掘り下げで見つけた事項は、照合前に独立して答えられる論点に分ける。それぞれについて、何をどの条件で決めるかを spec の用語で短く記述する。誰が、どの操作を、どの状態で行うか、どの例外を扱うかなど、答えが変わり得る違いを含める。カテゴリ名や論点の状態は照合用の記述から外す。

比較する論点があるときは、`skill_dir` にこの `speckit-grill-me` の `SKILL.md` があるディレクトリを指定し、`python3 "$skill_dir/scripts/decision_neighbors.py"` の標準入力に JSON を渡す。`known` には、今回の入力を処理する前に登録されていた全論点のセッション内 ID と最新の記述を入れる。マップが空なら空配列にする。`incoming` の各論点には、両方の配列を通じて重複しない仮 ID を付ける。スクリプトは各論点を、登録済みの全論点と、同じ `incoming` 内でそれより前にある論点と比較する。

```json
{
  "known": [{"id": "P1", "text": "決済確定前の返金を承認できるのは誰か？"}],
  "incoming": [
    {"id": "N1", "text": "決済が確定する前に、払い戻しを承認できる役割はどれか？"},
    {"id": "N2", "text": "決済確定後の返金を承認できるのは誰か？"}
  ]
}
```

`neighbors[仮ID]` にはコサイン類似度が正の候補が最大 3 件入る。記述の完全一致を先頭に置き、ほかの候補を今回の比較での類似度順に返す。完全一致でも判断には元の記述を使う。この例で「払い戻し」と「返金」が同じ操作を指し、決済確定の時点も同じなら、N1 には P1 の ID を使える。確定の前後で別々に承認ルールを決められるなら、現在の承認者が同じでも N2 には別の ID を付ける。

- `incoming` は入力順に処理する。候補に先行する仮 ID があれば、割り当て済みのセッション内 ID をたどり、その論点の原文と照合する。決定対象と適用範囲が同じで、どちらを決めても他方の答えが必ず定まる場合に、その ID を再利用する。他に該当する論点がなければ新しい ID を付ける。各仮 ID に対応するセッション内 ID を控え、その ID に根拠のあるカテゴリ・目標・観点を結び付ける。
- 新しい論点は、今回の入力に含まれる根拠を揃えてから状態を決める。既存の決定がなく、原文の記述が食い違う場合は Partial とし、候補を 1 件だけ Step 2 の事実ゲートへ送る。既存の論点で確定結果や保留理由が有効なら、状態と依存関係を引き継ぐ。記録済みの決定と矛盾する根拠が見つかった場合は、その論点の ID で矛盾を確認する。
- 言い換えた表現は候補から漏れることがある。点数が低い場合や候補に出なかった場合も、カバレッジマップと依頼マップに同じ対象・適用範囲の論点がないか確かめる。Python やスクリプトを利用できない場合、実行に失敗した場合も、元の記述から同じ基準で照合を続ける。

ベクトルはメモリ内で扱う。既定では Python の標準ライブラリだけで、単語、連続する 3 文字、比較演算子の TF-IDF を計算する。共通する表現が順位に影響するため、プロジェクトが同義と定めた語には両方の記述で正準用語を使い、同じ論点かどうかは原文に戻って確認する。

学習済みの埋め込みで言い換えの候補を探す場合は、`model2vec` が入った Python 環境を使い、`GRILL_ME_VECTOR_MODEL` に仕様の言語に対応したローカルの Model2Vec モデルディレクトリを指定する。モデルはオフラインで読み込む。読み込みや変換に失敗した場合、またはゼロベクトルや非有限値を含むベクトルが 1 件でもあった場合は、今回の入力全体を TF-IDF で比較する。出力の `backend` で実際に使った方式を確認できる。
