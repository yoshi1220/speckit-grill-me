# SpecKit Grill Me

目的：アクティブな機能仕様にある曖昧さや未決定事項を検出・削減し、明確化すること。

本ファイルの「面談規律（全ラウンド共通）」に従い、コアの `speckit.clarify` コマンドの仕事を上限なしにやり切る。spec.md の曖昧さを検出し、**いま聞ける質問（フロンティア）をラウンドとして管理しつつ 1 問ずつ順番に**問い、回答を spec.md に即時反映し、**全論点（decision point）が Clear / Resolved / Outstanding / Deferred のいずれかに確定し、ユーザーが納得するまで**ラウンドを繰り返す。

> **※ 用語（設計ツリー / 質問候補一覧 / フロンティア / ラウンド / カテゴリ / 論点状態 / カテゴリ集約状態 / カバレッジマップ / 依頼マップ / 中核決定と派生決定 / 帰結による確定 / 根拠のある要素とエージェントが追加した要素）については「用語集」を参照。**

**macOS / Linux + Bash 環境で `speckit.clarify` の代替として実行できることが要件。** 対応環境内では、clarify が生成する成果物・副作用（`## Clarifications` セクション、各セクションへの反映、書き込みごとの検証、`checklists/requirements.md` の再検証、extension hooks の処理、カバレッジ付き完了報告）を同じ形式で生成する。内部の聞き取りと収束のアルゴリズムは、より深く明確化するために意図的に異なる。

この互換性は**成果物と副作用**に対するものであり、公式 Spec Kit の全実行環境に対応する代替を意味しない。前提スクリプトは Bash 版に固定し、PowerShell / Python 版の自動選択やフォールバックは行わない。

## 言語設定

**ユーザーから別言語の指定がない限り、日本語でコミュニケーションする。** 質問、説明、進捗、spec.md は同じ言語で統一する。

## User Input

```text
$ARGUMENTS
```

空でなければ、優先して深掘りする領域の指定として扱う。

## 前提

1. 実行環境が macOS / Linux で、`bash` コマンド、`.specify/scripts/bash/check-prerequisites.sh`、Serena が利用できることを確認する。満たさなければ、このスキルの対応環境外であることを明示して中断する。Serena だけが利用できない場合は base 版を案内し、PowerShell / Python の別スクリプトへ切り替えない。
2. リポジトリルートで `bash .specify/scripts/bash/check-prerequisites.sh --json --paths-only` を **1 回だけ**実行し、`FEATURE_DIR` / `FEATURE_SPEC` を取得する。JSON が取れなければ中断し、エージェントに応じた `speckit.specify` の呼び出しを再実行するか、feature ブランチ環境を確認するよう案内する。
3. spec.md が無ければ中断し、エージェントに応じた `speckit.specify` の呼び出しを先に実行するよう案内する（ここで spec を新規作成しない）。
4. `.specify/memory/constitution.md`（プロジェクト原則）があれば読む。加えて、**作業対象に関係するものだけ** Serena メモリを読む（`read_memory` に渡す名前は `.md` を除いたもの。例: `domain/product_domain_knowledge`）:
   - サンプル
     - `.serena/memories/domain/product_domain_knowledge.md` — ドメイン用語集・ステークホルダー・業務フロー
     - `.serena/memories/domain/<topic>.md` — トピック別ドメイン知識（一覧は `list_memories`）
     - `.serena/memories/architectures/<topic>.md` — レイヤ構成・設計パターン・CI/CD

### Extension hooks（clarify と同一の処理）

`.specify/extensions.yml` があれば、質問開始前に `hooks.before_clarify`、完了報告前に `hooks.after_clarify` を処理する。ファイルが無い、またはその段階のフック登録が無い場合は黙ってスキップする。パース不能または不正な場合は黙ってスキップしない。`.specify/extensions.yml` を読み取れなかったこととパーサーのエラーを伝え、必須フック（`optional: false`）を含めフックを一切確認できていないと明示してから続行する。

- `enabled: false` のフックは除外（`enabled` 未指定は有効扱い）
- 非空の `condition` を持つフックは評価せずスキップ（HookExecutor に委ねる）
- フックのコマンド ID は、現在のエージェントの構文で呼び出す（例: `speckit.git.commit` は `/speckit.git.commit`、`/speckit-git-commit`、`$speckit-git-commit` のいずれか）
- `optional: false` → `EXECUTE_COMMAND: {command}` を出力し、実際にそのフックを現在のエージェント／セッションで起動して完了を待つ。出力だけで実行済みとみなさない
- `optional: true` → コマンド・説明・プロンプトを提示するだけ

## 用語集

本ファイル共通の用語。以降の Step はこの定義を前提に書いている。

### 設計ツリー

spec に残る未確定の決定（決めるべき論点）を、依存関係で親子につないだ木。面談の進行管理用にセッション内部で維持するモデルで、ファイルには書き出さない。

- **ノード** — 1 つの決定。セッション上の状態として、作業中の未解決（カバレッジの Partial / Missing）、確定（Resolved）、終端保留（Outstanding / Deferred）のいずれかを持つ。終端保留は今回の面談を閉じる状態であり、プロダクト上の決定が確定したことを意味しない。ユーザーの回答（または調査で判明した事実）で確定する。
- **枝** — 「親の決定が確定して初めて、子の決定が意味を持つ」という依存関係。例: 「対象範囲に◯◯を含めるか」（親）が決まらないうちは、「◯◯の一覧に何を表示するか」（子）は答えようがない。

質問候補一覧の各候補は、この木のいずれかの決定を確定させるための質問。初期形は Step 1 で作った質問候補一覧の各候補を Step 2 でノードと紐付けた時点にでき、以降は一覧に候補が増えるたびに対応する決定がノードとして加わり、回答・事実の確定でノードの状態が更新されていく（最初に作って固定する木ではない）。

親ノードが確定するたび、直下だけでなくすべての子孫ノードについて、その親決定の結果でも論点が成立するか、以前は成立しなかった論点が再び成立するかを両方向に再評価する。親依存を理由に子孫を非適用または終端保留へ変更する前に、その時点の論点状態・確定値・質問候補を「再開用情報」として現状態とは別に退避する。

成立しなくなった子孫は削除せず、**「非適用」という確定結果を持つ Resolved ノード**として残し、次を同じ処理内で行う。

- 対応する質問を現在のフロンティアと質問候補一覧から除く
- カバレッジマップ上の対応論点を Resolved へ変更し、「親論点〈論点〉の決定〈結果〉により非適用」のように根拠を記録する
- spec に子論点の古い記述が残る場合は、親を確定させた情報源に応じて Step 4A または Step 4B で削除・修正し、保存・検証する。親回答の Clarifications 記録とは別に、非適用になった子の Q&A は追加しない
- 設計ツリーとカテゴリ集約状態を再計算する

逆に、親決定の変更で、非適用または親依存の Outstanding / Deferred だった子孫が再び成立する場合は、親依存の終端理由を取り除いて次を行う。

- 退避した確定値が親の新しい結果でも有効で、現在の spec に反映・検証済みなら Resolved を維持する
- それ以外は、現在の spec と再開用情報から Partial / Missing を判定し直し、対応する質問候補を復元する。復元した候補には Step 2 の事実ゲート・影響度基準・依存関係評価を通常どおり適用する
- 再評価後のノード状態とカバレッジ状態を同じ処理内で更新し、設計ツリーとカテゴリ集約状態を再計算する

### 質問候補一覧

曖昧さスキャン（Step 1）で Partial / Missing の論点から作る、ユーザーに問う質問候補の全体プール。固定ではなく、追撃質問・決定の派生チェック・確定後の掘り下げ・再スキャン（Step 5）で候補が増え、調査で事実と判明した候補・既出回答で無効化された候補は落ちる。

### 質問候補の追加経路

質問候補一覧に候補が増える 4 つの経路。

| 経路                     | 説明                                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **追撃質問**             | 回答が曖昧・矛盾だったとき、同じ決定を精密になるまで問い直す質問（記録済みの決定との矛盾確認もこの形で出す）                                               |
| **掘り下げ**             | 選択肢が選ばれた結果として新たに生まれた決定点・境界条件を、納得まで確定させにいく質問                                                                     |
| **決定の派生チェック**   | ラウンド終了時に、確定した各決定を適用範囲の調査済み事実（対象種別・画面ごとの差異など）と突き合わせ、検討されていなかった不整合・境界条件を候補に足す検査 |
| **再スキャン**（Step 5） | 聞ける質問が尽きたとき、更新後の spec.md 全体を読み直し、回答が新しく露出させた曖昧さから候補を作る                                                        |

### フロンティア

質問候補一覧のうち、未解決の前提が残っておらず**いまなら答えられる**質問の集合（設計ツリーを根側から確定させていく際の最前線のイメージ）。決定が確定するたびに、それに依存して聞けなかった候補が新しくフロンティアに入れるようになる。

未完了の事実調査または未確定の親論点に依存してフロンティアへ入れない候補を**ブロック候補**と呼ぶ。ブロック候補は質問候補一覧に残り、「候補が無い」とはみなさない。Step 5 へ進む前に、Step 3 の Step 5 進入ゲートで依存元までたどって解消・終端化する。

### ラウンド

フロンティアを 1 単位とする面談の進行単位。ラウンド内は 1 問ずつ順に問い、ラウンドが終わるたびにフロンティアを取り直す。

### カテゴリ

曖昧さスキャン（Step 1）とカバレッジ報告（Step 8）は、次の 10 カテゴリで論点を整理する。カテゴリは複数の論点を束ねる集約単位であり、状態を直接確定する最小単位ではない。本ファイルで「全カテゴリ」と書いたときはこの 10 個を指す。

- **機能スコープと挙動**: コアゴールと成功基準 / スコープ外宣言 / ロール・ペルソナの区別
- **ドメインとデータモデル**: エンティティ・属性・関連 / 一意性・識別ルール / ライフサイクル・状態遷移 / データ量の想定
- **インタラクションと UX フロー**: 主要ユーザージャーニー / エラー・空・ローディング状態 / アクセシビリティ・ローカライズ
- **非機能品質**: 性能 / スケーラビリティ / 信頼性・可用性 / 可観測性 / セキュリティ・プライバシー / コンプライアンス
- **連携と外部依存**: 外部サービス・API と障害モード / 入出力フォーマット / プロトコル・バージョン前提
- **エッジケースと失敗処理**: ネガティブシナリオ / レート制限 / 競合解決（同時編集等）
- **制約とトレードオフ**: 技術制約 / 明示的トレードオフ・棄却済み代替案
- **用語の一貫性**: 正準用語（`.serena/memories/domain/` のドメイン用語集と照合）/ 避けるべき同義語
- **完了シグナル**: 受入条件のテスト可能性 / 測定可能な Definition of Done
- **その他**: TODO・未決マーカー / 定量化されていない曖昧形容詞（「堅牢」「直感的」等）

### 論点（decision point）と状態

状態はカテゴリではなく、カテゴリ内の個々の論点に付ける。上記カテゴリの各チェック項目（例: 性能、可観測性、セキュリティ）と、スキャンで新たに見つけた独立した決定事項をそれぞれ 1 論点として扱う。1 つの質問が複数の決定を含む場合も、状態は論点ごとに更新する。

| 状態            | 付ける場面                                            | 意味                                                                                                    |
| --------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **Clear**       | Step 1 のスキャン                                     | 最初から十分に定義済みで質問は不要                                                                      |
| **Partial**     | Step 1 のスキャン中、または確定済み論点の再オープン中 | 記述・決定が不足しているか矛盾確認中。質問・調査の候補にする作業中状態                                  |
| **Missing**     | Step 1 のスキャン中                                   | 必要な記述が無い。質問・調査の候補にする作業中状態                                                      |
| **Resolved**    | 回答・調査事実の反映後、または親決定で非適用の確定後  | Partial / Missing だったが、spec への反映・検証または非適用理由の記録を終えて解消した                   |
| **Outstanding** | 質問にしないと決めたとき                              | Partial / Missing のままだが、実装・検証戦略に実質影響しない                                            |
| **Deferred**    | 質問・調査を保留、または中断したとき                  | 面談規律の延期条件に従って plan 段階に委ねる、ユーザーが保留した、必要な事実を現時点で取得できない、または中断により意図的に未解消 |

Partial / Missing は作業中状態であり、終了時に残してはならない。終了条件は、**すべての論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定していること**とする。

### カテゴリ集約状態

カテゴリの表示用状態は、配下の全論点から機械的に集約する。集約状態で論点別状態を上書きしたり、隠したりしない。

1. 作業中は、Missing が 1 件以上なら `Missing`、それ以外で Partial が 1 件以上なら `Partial`。
2. 作業中状態が無く、Deferred が 1 件以上なら `Deferred`。
3. それ以外で Outstanding が 1 件以上なら `Outstanding`。
4. それ以外で Resolved が 1 件以上なら `Resolved`。
5. 全論点が最初から明確なら `Clear`。

例えば「非機能品質」で Performance が Resolved、Observability が Outstanding、Security が Deferred、残りが Clear なら、カテゴリ集約状態は Deferred とする。ただし Step 6 / Step 8 では Outstanding を含む論点別内訳も必ず併記する。

### カバレッジマップ

全論点の意味的同一性（カテゴリ・決定対象・適用範囲）、現在状態、確定結果または保留理由と、その論点が属するカテゴリの集約状態を対応付けた一覧。初回の曖昧さスキャン（Step 1）で作り、回答・調査事実の反映や状態変更のたびに更新する。Step 5 の再スキャンでも同じ一覧を維持し、作り直さない。設計ツリーと同じくセッション内部で維持し、ファイルには書き出さない。同じ論点について、設計ツリーのノード状態とカバレッジ状態は同じ処理内で更新する。ノードを作業中の未解決へ戻しながらカバレッジを Clear / Resolved / Outstanding / Deferred のまま残すことは禁止し、旧状態・旧確定値が必要なら現状態とは別の退避情報として保持する。終了条件は論点別状態で判定し、納得ゲート（Step 6）ではカテゴリ集約状態と Outstanding / Deferred の論点別サマリを提示し、完了報告（Step 8）では全カテゴリの集約状態と論点別内訳を出力する。

### 依頼マップ

spec.md の元の依頼と `$ARGUMENTS` が求めるすべての能力・制約・除外を、依頼の言葉で記録したセッション内の一覧。これらを**明示された目標**と呼び、各目標について次の 6 つの**中核観点**を追跡する。

1. **意味と単位** — 目標が何を意味するか。数える、または記録する単位、識別方法、キーを含む。
2. **アクターと権限** — 誰が実行し、誰が結果を変更でき、アクターを個人・役割・拠点・端末のどの粒度で記録するか。「物理的に起きたことの記録」「依頼・受諾・拒否・取下げ・終了」「訂正」「設定・担当者の指定データ・端末登録などのシステム管理」のように、操作の種類ごとの規則として確定する。判明済みの操作だけを列挙せず、後で確定する操作にも規則が適用されるようにする。管理操作を個別に聞くのは、明示された目標・確認済み事実・受諾済み決定が、同種の他の操作と異なる扱いを求める場合だけとし、権限規則を埋めるためだけに管理者ロールを追加しない。承認者や予算責任者など、指定された人または役割の担当者がいないとワークフローが進まない場合は、誰を担当者とするかを決める情報源・規則も対象にする。そのワークフローで起こり得る**担当者に関するケース**として、担当者が未指定、処理待ちの間に不在または交代、同じ案件で 1 人が依頼者を含む複数の役割を兼ねる、代理人が対応する場合を扱う。処理待ち案件の再割当てが可能なら、誰が許可し、その案件に何が起きるかも確定する。人ごとでなく役割ごとの規則にする。「待つ」「拒否する」も選択でき、ケースがあるだけで新しい仕組みを要するわけではない。業務上の役割を誰が担うかは要件であり、マスターデータ管理ではない。指定データの入力・保守方法は、ユーザーによる管理自体が明示された目標でなければ管理上の詳細とする。担当者の特定が必要なことから、管理者ロール・設定画面・ロール管理を推測して追加しない。
3. **データと状態への効果** — どの数量・記録・状態が、どのイベントや時点で変わるか。記録を訂正・取消できる場合は、その結果を別の当事者や端末の記録を含む後続記録がすでに反映しているとき、訂正・取消が数量と状態へ何をもたらすかも扱う。誰が訂正できるかを決めただけでは、この効果は確定しない。
4. **失敗と競合の結果** — 入力が不正、資源が不足、操作が競合、イベントの順序が逆転したとき、何を記録し、各当事者に何を見せるか。手順や当事者間の引渡しを含む目標では、**ワークフローの標準的な例外**も含む。完了前の取下げ・取消、一部履行と残りの終了、未着・紛失、発送量・約束量を超える受領や履行、重複送信、取消と発送の同時記録のように操作が行き違う場合を、観点 2 と同じく操作の種類ごとに確定する。複数端末や切断中に記録する場合は、切断中に記録できる操作の種類を同様に 1 種類ごとの規則で扱う。別拠点・別端末の記録を含め、当事者が頼るデータに必要な鮮度と、まだ最新でないデータの見分け方、記録の識別と重複排除、相手側の前段階の記録がまだ届いていないときに何を記録できるか（発送記録の同期前の受領など）も確定する。数量とワークフロー状態を含むその目標の全記録を順序付ける単一の基準（時計または連番）、その基準が信頼できない場合、端末の紛失・交換時の扱いも対象にする。
5. **現在の状態からの移行** — 既存のデータ・記録・業務に言及する依頼では、既存値の移行、切替時点、切替時の処理中案件、並行運用、ロールバック。
6. **検証** — 目標を満たしたと分かる観測可能な確認方法。目標自体が「即時」などの曖昧な品質を求める場合は、その測定可能な形を一度だけ問い、「数値目標を設けない」も選択肢に含める。除外の場合は「対象外と制限事項」の記録を対応付ける。

明示された目標の中核観点を確定する論点を**中核決定**と呼ぶ。掘り下げ・決定の派生チェック・再スキャンで後から見つかった論点も、選択肢が追加したものではなく、目標自体が管理する数量・状態、当事者がそれらに対して行える操作、頼るデータに必要な鮮度を変えるなら、その観点の中核決定とする。受諾済み規則から答えが導ける場合を除き、深さや段階にかかわらず質問し、Outstanding にしない。先に、その論点の原因となる要素を分類する。エージェントが追加した役割・設定・操作の管理だけに必要な論点は中核ではなく、スコープ拡張と延期の規則を適用する。権限の共通規則のように、1 論点で複数目標の同じ観点を確定してよい。同じ論点を複製しない。ワークフローの標準的な例外、切替時の処理中案件、観点 2 の担当者に関するケースは、目標自体が生む中核決定である。ワークフローの手順が確定した時点で候補を作り、前提がそろってから質問する。まず適用可能性を評価し、確定済みの手順では起こり得ない例外は、理由を付けて「非適用」の Resolved にし、質問しない（何も送らず数えもしないなら、超過も起きないなど）。起こり得るが資料に記載のない例外は、適用対象のままとする。それ以外の追撃・掘り下げ・派生チェック・再スキャンの候補を**派生決定**と呼び、元の目標と深さ（中核回答から生まれたものが 1、深さ 1 の回答から生まれたものが 2、以後同様）を記録する。派生決定は目標の文言、調査済み事実、受諾済み回答のいずれかを根拠とし、エージェントが想像しただけの状況は候補にしない。受諾済み決定と事実が答えを必然的に定める派生決定は、面談規律に従って**帰結によって確定**し、質問しない。依頼マップも設計ツリーと同じくセッション内だけで維持する。候補の追加・状態変更ごとに更新し、納得ゲートと完了報告で目標別カバレッジを提示する。

### 根拠のある要素とエージェントが追加した要素

選択肢が仕様に加える能力・役割・エンティティ・ワークフロー段階・マスターデータ操作・数値目標を、すべて分類する。

- **根拠のある要素** — 明示された目標または調査済み事実が、その要素についての決定を求めている。目標の中核観点を確定するもの、または資料が存在・発生を示す状況への対応が該当する。資料では存在するとされるのに記録で区別されていないバリエーション・版の区別、可用量や状態の変化を定める承認・予約・確認の段階、記録を訂正できる人の決定など。通常の選択肢として扱い、スコープ拡張とはみなさない。状態・操作・記録が増えるという理由だけで避けない。
- **エージェントが追加した要素** — 中核観点の確定に必要な範囲を超え、明示された目標にも調査済み事実にも求められていない。まれな境界事例のための仮登録・統合の仕組み、追加の管理者ロールや管理画面、通知、帳票、依頼が求めていない品質の数値目標など。他のエージェント追加要素が作り出した状況にだけ対応する要素も、この分類にする。

追加量ではなく、依頼と資料の内容で分類する。根拠のある要素をサポートしない選択は、中立的な既定ではなくスコープを狭める選択である。面談規律の「明示された目標を最もよく満たす案を推奨する」「エージェントが追加した要素を明示し、その詳細を面談へ持ち込まない」も参照する。

## 面談規律（全ラウンド共通）

- **共通理解に達するまで、あらゆる面を徹底的に面談する。** 表層の合意で切り上げない。
- **フロンティアはラウンド開始時に固定し、順に 1 問ずつ出す。** ラウンドの質問を一括提示せず、1 問提示して回答を待ち、反映してから次の 1 問を出す。ラウンドの全質問が済んでから次ラウンドへ進む。1 ラウンドの質問数に上限は設けない。ラウンド途中で質問を追加しない。
- **依存する質問は後のラウンドへ回す。** 同じラウンドでまだ解決していない質問に答えが左右される質問は、このラウンドに入れない。推測した前提の上に質問を積まない。前提となる質問が解決してから、次回以降のラウンドでフロンティアに入れる。
- **ラウンドが終わるたびに設計ツリーを再計算する。** ラウンド中の回答を設計ツリーに反映し、未解決の質問に依存していて聞けなかった質問候補のうち前提がすべて解決したものを、次のフロンティアへの追加候補にする。フロンティアの取り直しはラウンド終了処理（Step 3）で行い、ラウンド途中では行わない。
- **事実は聞かずに調べる。事実を見つけるのは常にこちらの仕事であり、ユーザーの仕事ではない。** コードベース・Serena メモリ・既存 spec で確認できる事実は自分で調べ、質問から除外する。ユーザーに問うのは、調べても答えが出ず、ユーザーにしか決められない**決定**だけ。調査は Serena のメモリツール（`read_memory` / `list_memories`）とシンボルツール（`find_symbol` / `find_referencing_symbols` など）で自分で行い、サブエージェントには委譲しない。
- **調査待ちでラウンドを止めない。** 済んでいない調査は未確定の前提と同じ。今ラウンドに間に合わない調査があれば、それに依存する質問だけをフロンティアから外して質問候補一覧に戻し（調査が済んでから、次回以降のラウンドで改めてフロンティアに入れる）、フロンティアに残った質問は引き続き今ラウンドで出す。
- **1 問では独立して選べる決定を 1 つだけ問う。** 一方は受け入れ、他方は拒否できる内容なら、フロンティアの固定前に別の候補・設計ツリーノードへ分ける。依存する決定は依存関係の規則に従って後のラウンドへ回す。1 つの決定と不可分な帰結は選択肢に含めてよいが、無関係な方針を一括承認させない。ユーザーが 1 回の回答で複数の決定を述べた場合も、Step 4A の規則に従って各決定を反映する。
- **選択肢を状況に応じて 1〜3 個、`A.` からのラベル付きで提示する。** 最適解が 1 つなら 1 個、実トレードオフがあるなら 2〜3 個。各選択肢に理由（1〜2 文）を添え、末尾に必ず自由入力の行を置く。ユーザーはラベル 1 文字だけで、推奨以外の選択肢も同じ手軽さで受諾できる。
- **`**推奨**` を付けたら必ず推奨理由を書く。** 最有力の選択肢を `**推奨**` 付きで `A` に置き、**なぜ他案よりそれを推すのか**（依拠した事実・既存実装・トレードオフの評価）を 1〜2 文で明記する。理由なしにマークだけ付けない。
- **推奨の根拠と出典を見える形にする。** 選択肢の前に、比較に使った内容を「確認済み事実」「受諾済み決定」「未確認の仮定」の見出しで列挙する。確認済み事実には、事実 ID、ファイルパス、「ラウンド n、Qk」のいずれかの出典を必ず付ける。典型的な数量、増加率、想定される入力の揺れ、「通常」の業務など、推論・見積り・もっともらしさに基づく内容は、明らかに見えても未確認の仮定であり、確認済み事実にしない。記載が無いことは「資料に記載がない」と表し、プロダクトの事実として断定しない。推奨案の具体的な利点と実質的な不利益を示す。数量・時間・順序の決定では、具体的な数字を使う計算例を「例」と明示して 1 つ示す。境界が分かりにくい場合も短い例を添える。未確認の前提が選択を左右するなら、事実ゲートで調査するか上流の決定を先に確定する。方針の推奨を受諾しても未知の事実が確認されたことにはならず、説明用の例は明示的に受諾されるまで要件にしない。確定済み回答の復唱だけを目的とする質問を追加しない。
- **自由記述はいつでも・どれだけ長くても可。** 選択肢外の回答・部分採用・条件付き回答（「A だが○○の場合は…」）を歓迎し、そのまま決定として扱う。
- **選択肢が選ばれても、掘り下げが必要なら次の選択肢セットを出す。** 選択の結果として新たな決定点・境界条件が生まれたら、質問候補一覧に足し、次回以降のラウンドでフロンティアに入れて納得まで掘り下げる。状態、別に数える数量、終了操作を追加する選択肢では、その状態をどう抜けるか、受諾済みのどの操作が数量を変えるか、終了後も待っていたイベントを記録できるかを、不可分な帰結として選択肢内に示し、後で問い直さない。新しい操作は抱き合わせない。追加内容が必要とする新しい操作は、質問化の閾値に従って別の論点にする。
- **上流の決定から先に確定させる。** スコープ、アクター、データの正とする情報源は下流の挙動や境界条件を左右するので、序盤のフロンティアは上流を優先する。初回を含む各フロンティアの固定前に、複数の決定を制約する論点を特定する。該当する場合は切替方法と時点、データの正とする情報源、責任を持つ担当者の指定方法、ワークフローの開始・完了点、移行するデータの範囲などを、観点・目標をまたいでもそれが制約する決定より先に置く。切替時の処理中案件など、それらに依存する決定は前提の確定を待つ。上流の論点自身に未確定の前提がある間はフロンティアへ入れない。
- **掘り下げる前に、すべての目標の中核観点を確認する。** フロンティアでは全目標の中核決定を先に、派生決定を後に並べる。派生決定は深さ 1 を深さ 2 より先にし、同じ深さでは元の目標の影響度順にする。どれかの目標にいま聞ける中核決定がある間は、深さ 2 以上の派生決定を出さない。深さ 2 は、面談のどの段階でも Step 5 の段階 2 の閾値も満たす場合だけ質問する。それ以外は下記の帰結規則で確定できれば確定し、できなければ Outstanding にする。深さ 3 以上も帰結で確定するか Outstanding にし、回答の精密化、記録済み決定との矛盾確認、ユーザーが挙げた論点だけを例外とする。依頼マップで中核決定に分類した論点には、これらの制限を適用しない。保留した派生論点はすべて納得ゲートで列挙し、Step 4C が求める場合は「対象外と制限事項」に記録する。資料で確定済みの文脈を聞き直さない。質問数の少なさを終了条件にせず、重要な追撃・調査・再スキャン・明示的な保留は残す。直前の回答に近い細部より、依頼の中で最も影響の大きい未確定事項に質問を使う。
- **帰結は質問せず確定する。** 受諾済み決定と調査済み事実から、派生論点の答えが必然的に導かれる場合は質問しない。受諾済み規則・状態・式を適用した結果であることが必要で、ほかのもっともらしい案が見当たらないだけでは足りない。Step 4C で根拠となる決定を引用した要件として反映し、反映内容の 1 行報告と納得ゲートで示して、ユーザーが修正できるようにする。導けなければ、深さと閾値の規則に従う質問にする。帰結によって新しい能力・アクター・状態・操作・閾値・境界・値を追加しない。追加が必要なら質問にする。誰が実行・承認・変更・訂正できるか、アクターをどう記録するか（観点 2）、切断中などの条件下でどの種類の操作を使えるか、受諾済み回答にない状態・遷移・終端結果（操作の行き違いの結果を含む）は、既存の受諾済み規則で扱えない限り帰結にしない。明白な案が 1 つに見えても質問し、その案を推奨する。権限、操作の可否、行き違いは観点 2・4 のとおり操作の種類ごとの規則として問い、後で確定する同種の操作・行き違いへは帰結として適用する。規則が扱っていない種類だけを再び問う。受諾済みの順序基準を後続 2 記録に適用する、受諾済みの再集計・訂正規則を後で確定した数量に適用するなど、同種の別ケースへの適用は帰結にできる。根拠は受諾済み回答と調査済み事実だけにし、別の帰結から導かない。
- **根拠が生んだ論点だけを聞く。** 派生候補を作るのは、目標の文言・調査済み事実・受諾済み回答が、その状況の存在を示すか含意する場合だけとする。「分割で到着する場合があると資料に書かれている」ことや、分割により残量が生じることは根拠になる。ワークフローの標準的な例外、切替時の処理中案件、観点 2 の担当者に関するケースは、目標自体が生む論点であり、単なる想像ではない。適用されるものはすべて質問するか、上記の帰結規則で確定する。制限事項として残すのは、ユーザーが決定を断った、または既存の保留規則に該当する場合だけとし、ターン節約のために質問を省略しない。資料にない配送先誤りのように、想像だけが根拠のまれな外部事象を、推奨付きでも質問にしない。重要に見える場合は「気づいたが質問しなかった状況」として納得ゲートで示し、Step 6 に従って spec に記録する。ユーザーは選択肢 2 で再オープンできる。
- **マスターデータ管理とレコード構成は運用上の詳細として扱う。** コード・バリエーション・拠点・ユーザーの登録や保守方法、目標と受入シナリオが必要とする以上の記録項目、画面レイアウトは、それ自体が明示された目標でなければ面談の決定事項にしない。担当者の指定データを含む記録の入力・保守方法はここに含むが、業務上の役割を誰が担うかは含めない。ワークフローの担当者は観点 2 で扱う。資料にマスターデータの保守方法があるなら「確認済みの前提」に出典とともに記す。無ければ既存手順があると仮定せず、該当論点を Outstanding にする。資料にマスターデータ管理の記載がなく、この仕様でも定義しないことを「対象外と制限事項」に一度だけ記録し、未記述の手順に依存する要件を作らない。
- **明示された目標を最もよく満たす案を推奨する。** 調査済み事実と既知の制約を守りつつ、目標をどれだけ十分かつ安全に確定できるかで推奨案を選ぶ。複雑さの少なさは、同じ程度に目標を満たす案同士の選択にだけ使い、状態・操作・記録が少ないことだけでは推奨しない。依頼側と履行側の引渡しを含む目標では、受諾・拒否、履行、終了など各当事者の約束を、双方から見える明示的な記録状態にする案を、責務が暗黙のままの案より優先する。システム外で処理する、制限として残すなど、スコープを狭める案が実行可能なら提示し、どの目標または調査済み事実を満たせなくなるかと、実務上の結果を示す。狭める案を推奨するのは、すべての目標が達成される、依頼がその要素を明示的に除外する、またはユーザーが縮小を求めた場合だけとする。既知のバリエーション混在など、資料が存在・発生を示す状況を無視する案は、これらの場合を除き推奨しない。ある目標の順序基準を受諾した後は、その目標の後続の順序・競合の決定でも同じ基準を推奨する。別の基準を使う選択肢は、その旨と各基準の適用範囲を明示する。
- **エージェントが追加した要素を明示し、その詳細を面談へ持ち込まない。** 追加要素を含む選択肢にはスコープ拡張と明記し、どの目標に役立つかを示す。その要素を加えずに決定できる案も最低 1 つ残す。拡張を推奨しない。その要素なしではどの案も目標を達成できないなら、根拠のある要素へ分類し直し、通常の選択肢として比較する。拡張を受諾したら、外から見える挙動とともに「合意済みの拡張」として spec に記録する。内部の詳細（下位状態、訂正・統合規則、管理操作）は、ユーザーが求めない限り掘り下げず、「合意済みの拡張。詳細は計画で扱う」を理由に Deferred とする。依頼自体が述べた「即時」などの曖昧な品質目標は、「数値目標を設けない」も含めて一度だけ定量化を問う。依頼にない品質目標は追加しない。
- **ユーザーに見える挙動が変わらないものだけを計画へ委ねる。** 「計画で扱う」は、保存・同期の仕組み、アルゴリズム、内部データ構成など、ユーザーが何をするか・見るか・いつ行うかを変えない実現方法に限る。切替時点、旧新記録の並行運用、ロールバック手順、承認段階、権限、誰が何を記録するかは面談の決定事項として確定するか、「計画で扱う」以外の理由で Outstanding / Deferred にする。決まらないと目標を検証できない論点を計画へ委ねない。
- **記録済みの決定との矛盾を検知したら、対象論点を再オープンして次ラウンドの先頭で確認する。** ユーザー回答・調査結果・再スキャンのいずれで見つけても、黙って spec を上書きせず、次を同じ処理内で行う。
  1. 対応する設計ツリーのノードを未解決へ戻す。
  2. カバレッジマップ上の同じ論点を Partial へ戻し、直前の状態と確定値は「保留中の旧確定値」として別に退避する。カテゴリ集約状態を直ちに再計算する。
  3. 「記録済みの決定との矛盾を検知したため、次ラウンドの先頭で確認します」と 1 行伝える。ユーザー回答が矛盾の発端なら、その回答は決着まで保留する。
  4. 旧決定を維持するか新しい内容へ変更するかを問う追撃質問を質問候補一覧に足し、次ラウンドの先頭候補にする。
  5. 決着まで対象論点を未解決の前提として扱い、それに依存するフロンティアの残り質問は質問候補一覧へ戻す。確認できる残りの質問だけ今ラウンドで出し切る。
  6. ユーザーの選択で決着した内容は Step 4A、調査事実だけで見かけの矛盾が解消した内容は Step 4B で反映・保存・検証する。その完了後に設計ツリーのノードを確定へ、カバレッジ状態を Resolved へ同時に変更し、退避した旧確定値を破棄してカテゴリ集約状態を再計算する。まだ曖昧なら Partial のまま追撃する。

- **回答が曖昧・矛盾なら追撃する。** 精密になるまで打ち切らない。境界を突くために仮想シナリオを作ってよいが、質問内で「仮定」と明示する。ユーザーが受諾するまではプロジェクトの事実・要件・決定として扱わず、spec にも反映しない。追撃質問は質問候補一覧に足し、次回以降のラウンドでフロンティアに入れて確認する。
- **先の質問を先出ししない。** 提示するのは現在の 1 問だけ。同一ラウンドの残りの質問も、将来のラウンドの質問を先に見せたり、並べて見せたりしない。
- **共通理解の確認が取れるまで、決定内容に基づいて動き出さない。** 反映先は spec.md だけで、plan・tasks・コードには着手しない。
- **ユーザーの中断シグナル（「stop」「ここまで」「一旦進めて」）は尊重する。** 新しい質問の提示を直ちに止めて「中断終了経路」へ移る。「終了」は質問ループの終了を意味し、チェックリスト・フック・完了報告を省略する意味ではない。

### 中断終了経路

spec の読み込み後にユーザーが中断を指示した場合は、面談のどの段階でも次を順に行う。

1. まだ受諾されていない回答は spec に反映しない。中断前に受諾・保存・検証済みの変更は維持する。
2. 現在の質問、未提示の候補、依存関係でブロックされた候補、未完了の事実調査、矛盾確認で再オープン中の論点を含め、残るすべての Partial / Missing 論点を Deferred へ変更する。理由を「ユーザーの中断」と記録し、対応する設計ツリーのノードを終端保留へ変更する。フロンティアと質問候補一覧を空にし、カテゴリ集約状態を再計算する。
3. 未解消内容を推測で補ったり、新しい Clarifications の Q&A を作ったりしない。目標の挙動を未定義のままにする Outstanding / Deferred の論点と、気づいたが質問しなかった状況のうち未記録のものを、目標ごとに 1 行、「未決（中断）」と明記して「対象外と制限事項」へ記録する。未決であることだけを述べる。その後、保存した spec に対して Step 4C の最終全体検証を行う。
4. Step 5 の再スキャンと Step 6 の納得ゲートは省略し、Step 7 のチェックリスト再検証へ進む。
5. Step 7 の後、Extension hooks の規則どおり hooks.after_clarify を処理する。必須フックは実際に起動して完了を待ち、任意フックは案内を出す。
6. Step 8 の完了報告を「ユーザー中断による完了」として出す。中断時点、Deferred にした論点と理由、納得ゲートで未確認と明記した帰結による要件、カバレッジ表、チェックリスト結果、フック処理結果、および plan へ進むか後で再実行するかの推奨を含める。

### 質問の形式

各質問は順に 1 問ずつ次の形式で出す。最初に目標や経験を一般的に説明させるのではなく、いま答えられる最優先の論点から選択式で始める。既知の文脈から具体的な選択肢を作り、自由記述の経路とユーザー自身が状況を説明したいという希望も尊重する。欠けた事実を仮定して選択肢を選べるようにしない。番号はラウンドごとに `Q1` から振り直す（ラウンドが変わったことが番号からも分かるようにする）。前ラウンドから持ち越した質問にも新しい番号を振り、提示時に持ち越しである旨を 1 行添える。

```text
❓ **Q1** - **<質問タイトル>**: <質問本文。前提の説明を含んでよく、複数段落でもよい>

- 確認済み事実: <事実（出典）>; <事実（出典）>
- 受諾済み決定: <ラウンド n、Qk — 要旨>
- 未確認の仮定: <選択肢の比較に使った仮定>

➡️
- **A. <選択肢>** — **推奨**。<推奨理由 1〜2 文>
- **B. <選択肢>** — <理由 1〜2 文>
- **C. <選択肢>** — <理由 1〜2 文>
- **自由入力** — 上記以外・部分採用・条件付き回答（分量無制限）
```

選択肢の数は 1〜3 個で状況に応じて増減し、`**自由入力**` の行は常に置く。根拠を示す 3 つの見出しは、該当内容が無いものだけ省き、別の種類の見出しへ移さない。ユーザーは提示中の 1 問に、「A」「B」などラベル 1 文字、「推奨で」、または自由記述で回答できる。「はい」は、この質問で何を意味するかが一意な場合だけ受け付ける。「スキップ」なら次ラウンドへ持ち越して番号を振り直す。「保留」なら「ユーザーが保留」を理由に Deferred とし、ユーザーが再オープンしない限り再質問しない。提示中の質問以外に触れる自由記述（後続質問への先行回答、確定済み決定の明示的な修正）もそのまま決定として受け付け、提示中の質問の回答と同様に Step 4A で各決定を反映する。フロンティアの取り直しはラウンド終了時だけ行う。番号はラウンド内の参照用で、spec.md には記録しない（Clarifications の形式は Step 4A のとおり）。過去のラウンドの質問に触れるときは「ラウンド n の Qk（<質問タイトルまたは要旨>）」の形で参照し、番号だけでは思い出せないため質問内容を必ず再掲する。

## Workflow

### Step 1. 曖昧さスキャン

spec.md 全体を読み、「用語集」の全カテゴリ内にある各論点について **Clear / Partial / Missing** を判定した内部カバレッジマップを作る。これは初回スキャン時だけの初期化である。Step 5 から再実行するときはマップを作り直したり全論点をこの 3 状態へ戻したりせず、Step 5 の状態照合規則に従う。カテゴリに直接 1 状態を付けるのではなく、論点別状態からカテゴリ集約状態を算出する。

同じスキャンで**依頼マップ**を作る。明示された目標を依頼の言葉で列挙し、各目標の 6 つの中核観点を spec と調査済み資料に照らして評価する。既存の文章が確定している場合だけ Clear とし、その文を記録する。Partial / Missing の各観点から、対応する目標を付けた中核決定の候補を作る。全観点が Clear の能力・制約にも、Step 4C により受入確認を対応付ける。

それ以外の Partial / Missing の各論点からも質問候補を作り、**質問候補一覧**にまとめる。除外するのは「実装・検証戦略に実質影響しない」「面談規律の延期条件に従い plan 段階に委ねるのが適切（内部メモに残す）」ものだけとする。事実で答えが決まるものはここで除外せず、Step 2 で調べて落とす。**質問数の上限は設けない。**

除外した各論点は Partial / Missing のまま残さず、カバレッジマップ上で **Outstanding** または **Deferred**（「用語集」の状態定義に従う）へその場で変更する。変更後にカテゴリ集約状態を再計算する。論点の状態を確定しないと Step 5 の終了条件に到達しない。

### Step 2. 事実ゲートとフロンティアの算出

質問候補一覧へ候補が追加されるたび、フロンティアを算出する前に、まだ事実ゲートを通過していない候補、および依存元の確定などで前提が変わった候補すべてへ、次の順序で**事実ゲート**を適用する。初回の Step 1 で作った候補だけでなく、追撃・掘り下げ・決定の派生チェック・再スキャンで追加された候補も対象にする。

1. 候補の答えを「調査で確定できる事実」か「ユーザーが方針として確定すべき決定」かに分類する。
2. 事実候補は、コードベース・Serena メモリ・既存 spec を自分で調べる。答えが確定した候補は質問候補一覧から落とす。調べた事実で spec の曖昧な記述が解消するなら **Step 4B** で spec 本体だけを直し、反映・検証後に対応論点を Resolved へ変更する。Clarifications には追記しない。
3. 事実調査が未解決の決定に依存する候補、または今ラウンド中に調査が完了しない候補は、質問候補一覧に「調査待ち」として残す。依存元の確定または調査の完了後に事実ゲートを再適用し、それまではフロンティアへ入れず、ユーザーへの質問にも変換しない。
4. 調査可能な情報源を尽くしても事実として確定できず、プロジェクトの方針・要件を新たに選ぶ必要があると分かった候補だけを決定候補へ分類し直す。外部に正解が存在する事実を単に取得できないだけなら決定扱いせず、実装・検証戦略への影響がない場合は Outstanding、それ以外は調査不能の理由を記録して Deferred にする。

事実ゲートを通過して決定候補として残った各候補へ、現在の段階の閾値（Step 5 の定義）を適用する。中核決定は常に通過する。閾値を満たさない候補を一覧から外す。段階 1 なら、回答がどう決まっても実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれも変わらない候補が該当する。外した候補は、帰結規則が許せば帰結で確定し、できなければ Outstanding / Deferred にする。目標の挙動を未定義にする場合は「対象外と制限事項」へ記録し、カテゴリ集約状態を再計算する。

残った決定候補を、その質問が確定させる設計ツリーノードと、依頼マップ上の目標・深さに対応付ける。**未解決の前提が残っていない候補**を質問候補一覧からフロンティアへ移し、ほかは一覧に残す。面談規律に従い、全目標の中核決定を先にする。その中では複数の決定を制約するものを優先し、次に影響度 × 不確実性の順にする。派生決定は後に置き、深さ、元の目標の影響度の順に並べる。「質問の形式」の規則で番号を振る。

### Step 3. ラウンドループ

現在のフロンティアを 1 つのラウンドとし、ラウンド内は 1 問 1 答で進める:

1. ラウンド開始時に「ラウンド n（m 問）」を 1 行で宣言する。前ラウンドで検知した矛盾の確認から始まるラウンドでは、その旨を宣言に含める（例: 「ラウンド n（m 問）— 記録済みの決定との矛盾の確認から始めます」）。質問の一覧は先出ししない。
2. 「質問の形式」に従い、まずはラウンドの先頭 1 問だけを提示してユーザーの回答を待つ（提示順は Step 2 の並び順。番号はこの順に Q1 から振ってあるため、昇順に進む）。
3. 回答が返ったら、確定した各決定を Step 4A で反映・保存し、対応論点を Resolved へ変更してから次の 1 問を出す。追加・変更した要件 ID とシナリオ ID、帰結で確定した要件、Clarifications の件数を「受諾済み回答 n 件中 n 件」の形で 1 行報告する。編集操作ではなく保存後のファイルの内容を伝え、保存前に取り消した中間編集には触れない。曖昧・矛盾のままの回答は追撃候補として後のフロンティアへ回し、今ラウンドへ差し込まない。保留の旨と理由を 1 行伝えてから次へ進む。スキップした質問は後のラウンドへ持ち越して番号を振り直し、保留した質問は「質問の形式」に従って Deferred にする。記録済み決定と矛盾する回答は、矛盾規律に従って保留し、確認の追撃を次ラウンドの先頭に置く。
4. 既出の回答がラウンド内の後続質問を確定していたら、その質問は提示せず、「既存の回答で確定したため回答済みとして反映した」と 1 行で伝える。後続質問の前提自体を成立しなくしていたら、「設計ツリー」の非適用規則を直ちに適用し、対応論点を Resolved へ変更してから「親決定により非適用になった」と 1 行で伝える。先の回答で後続質問の選択肢が成立しなくなったり、引用予定の事実が変わったりした場合は、保存済みの spec に基づいてその質問を組み立て直し、影響を受けた選択肢を削除・修正する。
5. ラウンドの質問が尽きたら**ラウンド終了処理**を行う: 「ラウンド n 完了 — 確定 x 件・持ち越し y 件」を 1 行で報告し、**決定の派生チェック**を行ってから、設計ツリーを再計算して Step 2 へ戻り、次のフロンティアを取り直す。派生チェックでは、このラウンドで確定した各決定を適用範囲の調査済み事実（対象種別・画面ごとの差異、一覧/詳細/履歴、項目構成、必須/任意など）と突き合わせ、決定が検討していなかった不整合・境界条件を質問候補一覧に足す。依頼マップも照合し、訂正・取消の追加などにより目標の意味、アクター、操作、状態への効果が変わったら、残りの観点とその決定を引用する受入確認を再評価する。追加操作についての観点 3・4 も対象に含める。

ラウンド終了後（初回の Step 2 でフロンティアが空だった場合も同じ）は、次の **Step 5 進入ゲート**を上から順に評価する。

1. フロンティアに候補があれば、Step 3 の次ラウンドへ進む。
2. 未完了の事実調査があれば、他の聞ける質問を妨げない範囲で調査を完了し、結果に Step 2 の事実ゲートを再適用する。調査不能なら Step 2 の規則どおり Outstanding / Deferred へ終端化する。Step 5 へは進まない。
3. 未確定の親論点に依存するブロック候補があれば、各候補から依存元を根側へたどり、次のように処理して Step 2 へ戻る。Step 5 へは進まない。
   - 作業中の親論点に対応する候補が質問候補一覧に無ければ、その Partial / Missing 論点から親候補を復元する。
   - 親論点が Clear / Resolved なのに子がブロックされたままなら適用条件を再評価し、適用される子を次のフロンティア候補にし、適用されない子には「設計ツリー」の非適用規則を適用する。
   - 親論点が Deferred なら、親の決着なしに確定できない子孫も理由付き Deferred として終端保留にする。親論点が Outstanding なのに実装・検証戦略へ影響する子孫があるなら、親を Partial へ再オープンして候補を復元する。子孫にも実質影響が無ければ Outstanding として終端保留にする。
   - 自己依存または循環依存を検出したら、依存グラフの誤りとして枝を組み直す。調査事実だけで順序を決められなければ、最も上流の決定を依存の無い根候補として置き直す。循環を残したまま再スキャンしない。
   - 状態変更後に設計ツリーとカテゴリ集約状態を再計算する。
4. **質問候補一覧が空で、未完了の事実調査もブロック候補も無く、すべての論点が Clear / Resolved / Outstanding / Deferred のいずれかである場合だけ** Step 5 へ進む。条件を満たさないのに進行可能な候補を復元できない場合は、残る作業中論点を理由付き Deferred として終端化してから、このゲートを再評価する。

### Step 4. 反映手順: spec.md への即時反映

Step 3 の次に実行する工程ではない。ユーザー回答が確定するたびに Step 3 から Step 4A を呼び、調査事実で曖昧さが解消するたびに Step 2 から Step 4B を呼ぶ。両経路を混ぜない。

#### Step 4A. ユーザー回答の反映

1. 初回のみ: spec.md の `## Clarifications` セクション（無ければ spec.md の概要セクション直後に作成）配下に `### Session YYYY-MM-DD` を用意する。
2. 受諾した回答ごとに `- Q: <質問> → A: <確定回答>` を 1 行追記する。後の受諾回答が過去の決定を変える場合は、古い行を残して ` → <後の質問の要旨> により更新: <新しい結果>` を spec の言語で末尾に付ける。本文に存在しなくなった決定を、更新の注記なしに Clarifications へ残さない。
3. 確定した決定を「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。
4. 1 回の回答に複数の決定が含まれる場合は、決定を 1 件ずつ反映・保存・検証する。ただし、同じ要件を変更する決定や相互に依存する決定は 1 回の保存で反映し、回答と矛盾する中間状態を保存しない。Clarifications の Q/A 行は受諾回答につき 1 行のままとし、同じ回答を重複記録しない。
5. 各決定の保存・検証が成功した後、その論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

#### Step 4B. 調査で確定した事実の反映

1. spec.md の `## Clarifications` / `### Session YYYY-MM-DD` を新設せず、Q/A 行も追記しない。Clarifications はユーザーとの質疑だけを記録する。
2. コードベース・Serena メモリ・既存ドキュメントから確認できた事実だけを、「Step 4C. 共通の反映・検証規則」に従って spec 本体へ反映する。推測や仮想シナリオは事実として反映しない。
3. 確認した事実を 1 件ずつ反映・保存・検証する。
4. 保存・検証が成功した後、その事実で解消した論点を Resolved へ変更し、カテゴリ集約状態を再計算する。

#### Step 4C. 共通の反映・検証規則

1. 内容を最適なセクションへ反映する:
   - 機能の曖昧さ → Functional Requirements
   - アクター・操作の区別 → User Stories / Actors
   - データ形状 → Data Model（順序を保ち、制約は簡潔に）
   - 非機能 → Success Criteria の測定可能な形（曖昧形容詞は指標へ変換）
   - エッジケース → Edge Cases / Error Handling
   - 用語 → spec 全体で正準用語に正規化（必要なら `（旧称 "X"）` を一度だけ）
   - 適切なセクションが無ければ、概要の散文へ追記せず、既存の最上位セクションと同じ階層に**標準の見出しを追加する**。プロジェクトのテンプレートに名前があればそれを使い、無ければ spec の言語で「アクターと権限」「機能要件」「データと状態」「エッジケースと失敗処理」「非機能要件」「受入条件」「対象外と制限事項」「確認済みの前提」を使う。「確認済みの前提」には Step 4B で反映した各事実と出典を記録する。元の依頼文は矛盾解消のための最小修正以外では変えず、既存セクションの改名・並べ替え・統合もしない。
   - すべての要件を、独立してテスト可能な番号付きの箇条書きとして書き、散文段落へ書き足さない。セクションごとの ID 接頭辞は、AP-（アクターと権限）、FR-（機能要件）、DS-（データと状態）、EC-（エッジケースと失敗処理）、NFR-（非機能要件）、SC-（受入条件）、OS-（対象外と制限事項）、VP-（確認済みの前提）とする。新規項目はセクション末尾へ次の番号で加え、上から読んで番号順になるようにする。既存 ID は振り直さず、削除による欠番は許容する。プロジェクトのテンプレートが独自 ID を定めていれば従う。通常 1〜2 文で規則だけを書き、背景・理由・質問を繰り返さない。帰結で確定した要件は根拠を引用する（例: 「ラウンド 2、Q1 と F04 から導出」）。状態変化は、契機となるイベント、変わる数量・状態、各当事者に見える結果を明示する。合意済みの除外・制限・拡張は理由とともに「対象外と制限事項」へ記録し、除外・制限には満たせなくなる目標または事実も示す。目標の挙動を未定義にする、気づいたが質問しなかった状況と Outstanding / Deferred の論点も、合意済み除外と誤読されないよう「未決」と明記し、1 件 1 行で記録する。論点・状態・理由と、ユーザー決定か不足する事実のどちらがあれば解消するかを示す（例: 「未決（未質問）: <状況> — <理由>; ユーザーの決定が必要」）。spec だけで未解消事項が分かるようにし、解消後はその行を削除する。
2. 新しい内容が過去の曖昧な記述を無効化するなら、重複追記ではなく**置換**する。矛盾する古い記述を残さない。後の決定が既存要件に例外・条件・別のケースを加える場合は、その ID の要件を直接修正し、別の場所から上書きする要件を加えない。新しい規則にだけ新規 ID を付ける。
3. **目標の挙動・境界・失敗結果を定める各決定から、受入確認を導く。** 「受入条件」へ番号付きシナリオ（例: SC-004）を 1 行で加え、前提、操作、観測可能な結果を、区別に必要な最小限の数量で述べる。検証する決定を引用する。数字だけが異なるシナリオは統合する。除外・対象外のシナリオは作らず「対象外と制限事項」に記録する。「拒否しなければならない」操作は除外でなく制約なので、拒否を確認するシナリオを作る。受諾済みの値だけを使う。数量は「例」と明記し、特定の数字に結果が依存しない場合に限り例示してよい。確認項目から新しい要件を生まない。未受諾の閾値・目標・能力が必要ならシナリオは書かず、その値の質問候補を作り、「数値目標を設けない」も選択肢に入れる。
4. **反映のたびに spec.md を保存する。** 全体を書き直さず、該当行だけを挿入・置換し、保存済み差分が意図した行だけを変えていることを確認する。無関係なセクションの並び・見出し階層は変えない。追記は最小限かつテスト可能な形に保つ。
5. **保存のたびに検証する**（最終ラウンド後にも全体パスを 1 回）:
   - Step 4A では保存したファイルを読み直して Clarifications の行数を数える。受諾済み回答につき重複のない 1 行が必要で、ここまでの受諾数と異なるなら次の質問前に修復する。Step 4B では Clarifications に差分が無いことを確認する
   - 要件・シナリオ ID が spec 内で一意かつセクション内で昇順で、別セクションの要件による上書きがない。更新された旧決定の要件とシナリオも同じ処理で修正されている
   - 数量とワークフロー状態を含め、1 つの目標の全記録が同じ基準で順序付けられている。異なる基準がある場合は、各適用範囲を仕様に明示し、組合せを受入シナリオで検証している
   - 反映内容が解消するはずだった曖昧な記述・プレースホルダが残っていない
   - 無効化された選択肢・矛盾する古い記述が残っていない
   - Markdown 構造が正しい。新設見出しは上記の標準セクションと、Step 4A の `## Clarifications` / `### Session YYYY-MM-DD` だけに限る
   - 新規要件はすべて番号付きで、各受入シナリオが受諾済み決定を引用し、未受諾の値を使っていない。Clarifications に更新注記のないまま本文と矛盾する行がない
   - 更新した全セクションで正準用語が一貫している

### Step 5. 再スキャンループ

Step 3 の Step 5 進入ゲートを通過した場合だけ、**更新後の spec.md に対して Step 1 の検出スキャンをやり直す**（回答が新しい曖昧さ・派生論点を露出させるため）。再スキャンは**初回実行と同じ厳しさで、更新後の spec を初見のつもりで**行うが、論点状態は初期化せず、次の順序で既存カバレッジマップへ差分統合する。

1. 再スキャン前の各論点について、意味的同一性・現在状態・確定結果または保留理由・依存関係を保持する。
2. 検出した論点を意味的同一性で既存論点と照合する。既存論点は別表現でも同じ決定対象と適用範囲なら同一とみなし、新規論点として作り直さない。
3. 既存の Clear / Resolved / Outstanding / Deferred 論点は、更新後の spec が記録済みの結果を支持し、新しい適用範囲・境界条件・矛盾が無い限り、状態と根拠をそのまま維持する。新しい矛盾などが見つかった場合も確定状態を黙って上書きせず、「記録済みの決定との矛盾を検知したら」の確認フローへ渡す。
4. 既存論点に対応しない本当に新しい論点だけを Clear / Partial / Missing へ分類し、新規の Partial / Missing から質問候補を作る。既存論点が本文から見つからない場合も自動削除せず、親決定による非適用なら「設計ツリー」の非適用規則、それ以外なら矛盾候補として扱う。
5. 差分統合後にカテゴリ集約状態を再計算する。

合格基準は「直後にこのスキルを再実行しても、決定を変え得る新しい質問が出ない」状態。新たな Partial / Missing の論点が見つかれば質問候補一覧に候補が補充され、聞ける質問が再び生まれるので、Step 2〜4 の新ラウンドへ。再スキャンで聞ける新しい質問が生まれず、全論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定するまで繰り返す。

ただし、再スキャンのたびに軽微な論点から新しい質問が生まれ続けて、面談がいつまでも終わらなくなる事態は避ける。検出の厳しさは保ったまま、**質問化の閾値を段階的に上げる**。

再スキャンで生成した候補は意味的重複を検査する。過去に Resolved / Outstanding / Deferred へ確定した論点と意味的に同一で、回答が同じ決定結果に収束し、新しい適用範囲・境界条件・矛盾も無いなら、新規候補として追加しない。表現が異なるだけの言い換えも重複とみなす。

> **※ 閾値の定義** — 「候補を質問として出すために、回答が何を変え得る必要があるか」の基準。次の 2 段階を使う。
>
> - **段階 1 — 中核観点の確認が完了するまで** — 回答次第で実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれかが変わる論点を質問にする。初回スキャンから Step 2 で適用する。
> - **段階 2 — 中核観点の確認が初めて完了したラウンド終了時から、遅くとも 2 回目の再スキャンから** — すべての目標の 6 つの中核観点が、標準的な例外と切替時の処理中案件も含め、依頼マップ上で終端状態になったら中核観点の確認完了とする。それ以降は、依頼・資料・ユーザーの発言が示す状況（2 端末が同じイベントを記録する場合など）で、回答によって当事者が行えること・見るもの、またはデータ整合性・セキュリティ・コンプライアンス上の責務が変わる論点だけを質問する。選択肢が追加した状態・数量・操作の維持だけに必要で、掘り下げ規則に従ってその選択肢内で述べる範囲を超えた論点（新設した数量を減らす新しい操作、別の操作がその数量を数えるかなど）、および受諾済み規則から帰結で確定できる論点は質問しない。帰結規則が許せば確定し、できなければ Outstanding として Step 6 に列挙し、Step 4C が求める場合は「対象外と制限事項」へ記録する。ユーザーは選択肢 2 で再オープンできる。どの段階でも、回答を精密にする追撃、記録済み決定との矛盾確認、未確定の中核決定は常に質問する。標準的な例外、切替時の処理中案件、担当者に関するケース、依頼マップが中核と分類する論点を含み、受諾済み規則から答えが導ける場合だけを除く。

Step 5 を終える前に、依頼マップと「受入条件」を照合する。明示された能力・制約には最低 1 つの受入シナリオを、除外には「対象外と制限事項」の行を対応付ける。目標の失敗・競合の結果を確定した場合も、関係する一部完了、再試行・重複送信、同じ記録への同時操作、順序が逆転したイベント、未同期記録との照合をシナリオで検証する。既存決定だけで足りるなら Step 4C で不足シナリオを導き、足りなければ必要な決定の候補を作って再スキャンの閾値を適用する。ワークフローの標準的な例外、切替時の処理中案件、観点 2 の担当者に関する各ケースが、確定済み、理由付きの非適用、または制限として記録済みであることも確認する。いずれにも当たらないものには中核決定の候補を作る。目標の挙動を変えるため、段階別の閾値によって保留しない。

### Step 6. 納得ゲート

全論点が Clear / Resolved / Outstanding / Deferred のいずれかに確定したら、まず Outstanding に、目標の数量・状態・許される操作・必要なデータ鮮度を変えるものがないかを確認する。あれば中核決定へ分類し直して Step 2 へ戻る。次に、気づいたが質問しなかった状況と、目標の挙動を未定義にする保留をすべて、Step 4C の 1・4・5 に従い、Clarifications の行を追加せず「対象外と制限事項」へ記録する。その後、全カテゴリの集約状態、依頼マップの 6 観点の目標別カバレッジ、Outstanding / Deferred の論点別サマリ、帰結で確定した要件とそれぞれの根拠、気づいたが質問しなかった状況、変更セクション、計画へ進めるかを提示する。Deferred の中核決定が実装または受入検証を妨げる間は、計画へ進める状態ではない。受諾回答・要件・シナリオなど保存内容の件数は、すべて保存済みファイルから取得する。**AskUserQuestion 等の対話 UI で選択肢を出して納得を確認する**。対話 UI が無ければ同じ 3 案を通常の応答へ出して選択を待つ。自由入力の「OK」待ちにしない。この固定形式は納得ゲートだけに適用し、Step 3 の質問は面談規律の形式に従う。

選択肢は次の 3 つで固定し、推奨には理由を添える:

1. **完了して次へ進む** — **推奨**。全論点が終端状態で、未解決の質問が残っていないため。これを選ぶと、上記の帰結による要件も受諾する。計画へ進める状態でない場合は、この選択は面談を終えるだけであり、妨げとなる論点が確定するまで計画を待つべきことを明示する
2. **追加で掘り下げたい領域がある** — 領域と具体的な懸念を聞き取り、該当論点（必要なら新しい論点）を Partial にして質問候補一覧へ足し、Step 2 へ戻る
3. **気になる領域は残るが、ここで打ち切る** — 領域と具体的な論点を聞き取り、「中断終了経路」の 2 以降に従って、その各論点を Deferred として記録したうえで Step 7 以降の後処理へ

1 が選ばれたら Step 7 へ進む。

2 が選ばれたら、掘り下げたい領域と気になっている内容を自由記述で答えてもらう確認質問を出し、回答の内容を確かめてから上記 2 の処理（該当論点を Partial にして質問候補一覧へ足し、カテゴリ集約状態を再計算して Step 2 へ戻る）に入る。

選択肢外の自由記述（追加論点の直接指摘など）が返ってきた場合も受け付け、内容に応じて 2 または 3 と同じ扱いにする。

### Step 7. チェックリスト再検証

`FEATURE_DIR/checklists/requirements.md` があれば（無ければ黙ってスキップ）:

1. コードフェンス外のチェックボックス行（`- [ ]` / `- [x]` / `- [X]`、ネストのインデント許容）だけを対象に、現在の状態と項目テキストを before スナップショットとして記録する。
2. 各項目を**更新後の spec** に対して再評価し、状態が変わる項目だけ `[ ]`/`[x]` を切り替えて保存する。見出し・メタデータ・注記・行順・空白など他は一切変更しない（差分ノイズを出さない）。
3. before との比較で 3 リストを作る: **新規通過**（unchecked → checked）/ **退行**（checked → unchecked）/ **未通過のまま**。before/after の通過数（例: 12/16 → 15/16）も記録する。

### Step 8. 完了報告

（after_clarify フックの処理を済ませてから）以下を報告する:

- 終了種別（通常完了 / ユーザー中断）。中断の場合は中断時点と、中断後の質問・回答を反映していないこと
- ラウンド数、提示した質問数、受諾回答数。受諾回答数は記憶でなく保存済み Clarifications から数え、スキップ・保留・追撃で再質問したものは別記する。ラウンド別内訳を添えてよく、質疑一覧は Clarifications を参照してよい。帰結で確定した要件は別に列挙する
- 更新した spec のパスと触れたセクション一覧
- チェックリストの before/after 通過数、新規通過・退行した項目、未通過のまま残った項目（要注意領域として列挙）
- カバレッジ表 — 全カテゴリの集約状態を **Resolved** / **Clear** / **Deferred** / **Outstanding** のいずれかで示し、カテゴリごとに論点別状態の内訳を併記する。Partial / Missing の論点が 1 件でも残っているなら完了報告へ進まない
- 依頼マップ表 — すべての目標について 6 観点それぞれの状態、検証する受入シナリオ（除外は「対象外と制限事項」の行）、関連する合意済み拡張・記録済み制限を示す
- Outstanding / Deferred が残る場合は、エージェントに応じた `speckit.plan` の呼び出しへ進むか後で再実行するかの推奨。終端状態は決定の確定を意味しない。実装・受入検証を妨げる Deferred の中核決定を 1 件ずつ示し、1 件でも残る間は計画へ進むのでなく、確定できるようになってからこのスキルを再実行するよう推奨する
- 次コマンドの提案（通常はエージェントに応じた `speckit.plan` の呼び出し。例: `/speckit.plan`、`/speckit-plan`、`$speckit-plan`）

## Behavior rules

- このワークフローは `speckit.plan` の**前に**完了している想定。ユーザーが明示的にスキップして先へ進む場合は、下流での手戻りリスクが上がることを警告した上で従う。
- 有意な曖昧さが無ければ「クリティカルな曖昧さは検出されませんでした」と報告し、全論点が Clear であるカテゴリ集約サマリを出して Step 6 の納得ゲートへ進む（無理に質問を作らない）。
- 機能の明確化をブロックしない限り、技術スタックの推測質問はしない。
- このスキルが変更してよいのは spec.md と `checklists/requirements.md`（Step 7 のチェックボックス更新のみ）だけ。plan / tasks / コード など他のファイルは変更しない。
