# SpecKit Grill With Docs

**必須**: 先に `../speckit-grill-me/SKILL.md` を最後まで読み、その手順に従う。

同じ親ディレクトリにある `speckit-grill-me` を**ベーススキルとして**実行する。手順（言語設定・前提・Extension hooks・用語集・面談規律・中断終了経路・Workflow Step 1〜8・Behavior rules）、成果物、終了条件はすべてベースのとおりとし、コアの `speckit.clarify` コマンドの代替として、成果物の互換性も維持する。

本ファイルで使う用語（論点・論点状態・質問候補一覧・フロンティア・ラウンド・設計ツリー・カバレッジマップ・依頼マップ・中核決定と派生決定・帰結による確定・根拠のある要素とエージェントが追加した要素）はベースの「用語集」の定義に従う。

本スキルがベースへ追加する責務は 1 点だけである。**面談中に確定した用語と、記録条件を満たす業務ドメイン・技術構成の決定を、その場で Serena メモリへ正しく永続化する。** 以下の追加規律は、すべてこの責務を実現するためのものとする。

ベースの Behavior rules にある「変更してよいのは spec.md と `checklists/requirements.md` だけ」は、本スキルでは**下表のメモリを加えた範囲**に読み替える。plan / tasks / コードを変更しない点は変わらない。

## ベースの明確化規則の適用

- 設計ツリー、カバレッジマップ、依頼マップはセッション内だけで維持する。掘り下げる前に、すべての目標の 6 つの中核観点を確認する。ドメインの質問にも、ベースの事実ゲート、依存順序、固定ラウンド、根拠提示、深さ制限、段階別閾値を適用する。知識の記録欄を埋める必要があることを、質問の根拠にしない。
- 番号付き要件、出典付きの確認済みの前提、決定から導く受入シナリオ、「対象外と制限事項」の未決事項は `FEATURE_SPEC` に残す。知識の成果物を、これらの記録や目標別カバレッジ、計画へ進めるかの確認の代わりにしない。

  Clarifications は受諾回答につき 1 行とし、調査事実・帰結の Q/A を追加しない。同じ要件を変える決定や相互に依存する決定は、ベース Step 4A の例外に従って spec へ 1 回の保存で反映する。受諾回答と矛盾する中間状態を保存しない。独立した知識項目は個別に処理する。
- 帰結で確定した要件は、新しいユーザー方針を決めたものでも、未知の事実を確認したものでもない。spec に元の受諾済み決定と調査済み事実を引用し、既存規則を適用しただけで新たな決定記録を作らない。

  ベース Step 6 の納得ゲートでユーザーが帰結を受諾するまでは、必須の記録先は spec だけとする。この段階では、知識の更新を待たずに、その論点を Resolved にしてよい。

  受諾後は、記録対象となるプロジェクト横断の用語・規則を、同じ出典とともに永続化する。対象成果物をすべて検証してから Step 7 へ進む。決定記録の記録条件は維持し、受諾だけで新しいトレードオフがあったとはみなさない。
- Outstanding / Deferred の論点、気づいたが質問しなかった状況、未確認の仮定、未受諾の仮想シナリオを、確定済みのドメイン知識にしない。ベースの規則に従って spec とカバレッジ報告へ残す。合意済み拡張は受諾された範囲とともに記録し、計画で扱うことにした内部詳細を、知識として確定した決定に変えない。
- 中断時は、保存済み spec の帰結を維持し、完了報告で納得ゲート未確認と明示する。受諾なしに正準知識へ昇格させない。受諾・保存・検証済みの知識変更は維持する。永続化に失敗した場合は、「永続化失敗時の扱い」に従う。

## 書き込み先

このリポジトリのドメイン知識と技術構成の決定は、**`.serena/memories/` 配下の Serena メモリを正準な記録先**とする。別の保存先を選ぶための判定や分岐は行わない。

| 確定した内容            | 書き込み先                                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 用語・概念の定義（ユビキタス言語） | `.serena/memories/domain/product_domain_knowledge.md` の該当節。トピックとして大きければ `.serena/memories/domain/<kebab-slug>.md` を新規作成する                                                                                                                               |
| 業務ドメインの設計決定       | `.serena/memories/domain/`（同上の粒度で判断）。後述の記録条件 3 つをすべて満たすものだけ                                                                                                                                                                                            |
| 技術構成の決定           | `.serena/memories/architectures/architecture_patterns.md` の該当節。トピックとして大きければ `.serena/memories/architectures/<kebab-slug>.md` を新規作成する。後述の記録条件 3 つをすべて満たすものだけ |

- **書き込み先は上表に限る。** 別のドメイン文書をリポジトリ内に新設しない。
- `domain/product_domain_knowledge` が存在する場合は、ベースの「前提」4 で読む Serena メモリへ**必ず含める**。加えて、対象 feature に関係するトピック別メモリを読む（後述の衝突検知に必要なため）。基幹メモリが存在しない場合は、次の遅延初期化規則に従う。
- 最初の読み取り前に `list_memories` で `domain/product_domain_knowledge` の有無を確認する。存在しなければ、既存の用語集は空として扱う。その場合に限り、最初の記録対象となる用語・概念が確定した時点で、そのメモリをプロジェクトの文書言語と既存メモリ規約に合わせて作成する。

  `architectures/architecture_patterns` も、存在しない場合に限り、最初の記録対象となる技術構成の決定が必要になった時点で作成する。基幹メモリが一覧に存在するのに読めない場合は、存在しないものとして扱わず停止する。
- **読み書きは Serena のメモリツールで行う。** 読み取りは `read_memory`、既存メモリの更新は `edit_memory`、新規メモリの作成は `write_memory` を使う。上表のパスは実体の所在を示す。`memory_name` には、そのパスから `.serena/memories/` と `.md` を除いた名前を指定する（例: `domain/<slug>` / `architectures/<slug>`）。**`.md` 拡張子を付けない。**
- 既存メモリを更新するときは、そのメモリの構造を維持して該当節だけを直す。トピック別メモリを新規作成するときは、タイトルを短く安定した決定・概念名にし、冒頭に結論を一文で記載する。関連メモリや根拠となる実装の一次情報パスが存在する場合は併記する。メモリ間の参照は `mem:<name>` 形式で書く（例: `mem:domain/vehicle-category-unified-master`）。存在しない参照や実装パスを推測・捏造して記載しない。
- トピック別メモリを作るのは、1 つの概念群または決定について複数の境界、不変条件、業務ルール、代替案、トレードオフを説明する必要があり、基幹メモリの簡潔な記載では意味を損なう場合に限る。判断に迷う場合は基幹メモリに留め、分割自体を目的にしない。
- 書き込みのたびに、同じ `memory_name` を `read_memory` で読み戻す。確定内容の正準な定義または決定記録が、意図したメモリ内に 1 つだけ存在し、別の正準記録として複製されていないことを確認する。正準記録への参照や定義済み用語の使用は重複に数えない。既存構造を壊していないことも確認する。
- 既存の更新先を読めない・書けない場合、または必要な新規メモリを作成できない場合は、他の場所へ書かず、その旨を報告して止める。

## 情報源の権威

情報源の権威は、内容の種類ごとに次のように扱う。

| 内容                      | 正とする情報源                                                   |
| ----------------------- | --------------------------------------------------------- |
| プロジェクト原則                | 存在する場合の `.specify/memory/constitution.md`。他の要件・決定に対する上位制約 |
| feature 固有の要件・期待挙動      | 現在の `FEATURE_SPEC` と、このセッションでユーザーが明示的に確定した決定              |
| feature を超えるドメイン用語・設計決定 | Serena メモリ。ただし、このセッションでユーザーが変更を明示的に確定した場合は、保存・検証後の新しい決定   |
| 現在の実装状態                 | 実コード・スキーマ・マイグレーション・テストなどの一次情報                             |

- constitution が存在する場合、それに反する回答は確定扱いにしない。対象論点を再オープンし、原則に適合する決定を確認する。constitution 自体の変更は本スキルの範囲外とする。
- ユーザーが constitution との矛盾を理解したうえでその決定を維持する場合は、本スキル内では解消不能として対象論点を理由付き Deferred にする。constitution の変更または例外承認が先に必要であることを記録し、constitution に反する内容を spec または Serena メモリへ確定事項として書き込まない。
- ユーザーの新しい回答は、提案・曖昧・矛盾確認中の段階では既存記録を上書きする権威を持たない。ベースの矛盾確認規律を通り、Step 4A による spec への反映・保存・検証と、必要なメモリの保存・検証をすべて完了してから、新しい決定を正とする。
- 現在の実装事実は、それ自体を望ましい要件や設計決定とはみなさない。異なる種類の情報源が矛盾する場合は、どちらかを黙って優先して上書きせず、ベースの矛盾確認規律に従って対象論点を再オープンする。

## 書き分けルール（spec と Serena メモリの二重管理を防ぐ）

| 内容                                | 書き込み先                                                                                    |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| この feature 固有の要件・挙動・エッジケース・受入条件   | ベースの前提で取得した `FEATURE_SPEC`（ベースの Step 4A / 4B / 4C の反映・検証規則どおり） |
| feature を超えて通用する用語・概念の定義          | ドメイン用語集メモリ（「書き込み先」の表）                                                                           |
| 覆すコストが高く、将来の読者が「なぜ？」と思う実トレードオフの決定 | 決定記録メモリ（「書き込み先」の表）。次の 3 条件をすべて満たすときだけ: ①覆すコストが実質的に高い ②判断の背景を知らない将来の読者には、その決定が意外に見える ③実際に代替案があり、理由をもって選んだ結果である   |

- 同じ内容を spec 本体とメモリの両方で**正準定義として**管理しない。feature を超えて通用する用語の正準定義は Serena メモリだけに置く。spec 本体ではその用語を使い、feature の理解・検証に必要な最小限の文脈や feature 固有の制約は記載してよいが、正準定義そのものを複製・再定義しない。

  決定については、feature 固有の要件・帰結だけを spec 本体へ、feature を超えて残す理由・トレードオフだけを決定記録メモリへ書く。ベースの Step 4A が要求する Clarifications の Q/A 行は監査記録なので、この二重管理には数えず省略しない。
- 同じ確定事項を用語集・概念メモリと決定記録メモリの両方へ書く場合、用語集・概念メモリには現在の意味、境界、業務ルールだけを、決定記録には採用理由、代替案、トレードオフだけを記録する。同じ説明を正準情報として複製せず、必要なら `mem:<name>` で参照する。
- Serena メモリへの書き込みも、spec と同じく**確定のたびに即時保存する**。1 回の回答で独立した複数の用語・決定が確定した場合も 1 件ずつ書いて保存する（まとめ書きしない）。
- 1 件の確定事項から複数成果物の更新が必要な場合は、① spec、②用語集または現在のドメイン知識メモリ、③業務ドメインの決定記録メモリ、④技術構成の決定記録メモリ、⑤全対象の読み戻し検証、の順で処理する。不要な成果物の手順は飛ばす。必要な処理がすべて成功してから、その論点を Resolved にする。
- Step 4A で確定した 1 件がメモリへの記録対象でもある場合は、spec の保存・検証後、対応するメモリの保存・読み戻し検証を完了する。その後、その論点を Resolved へ変更して次の質問へ進む。

  メモリの保存または検証に失敗した場合は Resolved にせず、別の場所へフォールバックせずに停止する。feature 固有の内容だけなら、ベースの Step 4A の順序を変えない。
- ベースの Step 4B だけで確認した実装事実を、業務ドメインまたは技術構成の「決定」として Serena メモリへ昇格させない。実装事実から feature を超える設計判断を新たに記録する必要が生じた場合は、ユーザーが決定すべき論点として質問候補一覧へ追加し、受諾後にだけメモリへ書く。

### 永続化失敗時の扱い

spec と Serena メモリへの反映は単一トランザクションではない。いずれかの成果物を保存した後、別の必要成果物の保存または検証が失敗した場合は、その論点に **「永続化未完了」という、永続化の進捗を示す補助状態** を付与して停止する。

「永続化未完了」はベースの論点状態ではない。帰結の受諾後の更新などで論点がすでに Resolved の場合は、確定値を別に退避し、設計ツリーのノードとカバレッジ状態を同じ処理で Partial に戻す。対象論点の設計ツリー／カバレッジマップ上の状態は Partial のまま維持し、spec と必要な Serena メモリの両方の保存・検証が完了するまで Resolved にしない。

回答を受諾すること、spec へ保存すること、メモリを保存・検証すること、論点を Resolved に変更することは、それぞれ別に管理する。

- 停止時に、対象論点、確定内容、保存・検証済みの成果物、未反映または未検証の成果物、失敗内容、次に必要な復旧操作を明示する。
- 同一セッションで再開する場合は、新しい質問を始める前に未完了の保存・検証をすべて終える。保存済みの成果物も読み直し、重複や新しい矛盾がないことを確認してから Resolved にする。
- 新しいセッションでは、Step 1 の質問候補を作る前に、最新の Clarifications にある用語・記録対象決定と関連する Serena メモリを照合する。未反映内容を一意に再構成でき、既存記録とも矛盾しなければ、該当する成果物へ反映・検証する。既存記録と矛盾する場合はベースの矛盾確認規律へ渡し、確定内容を一意に再構成できない場合は推測せずユーザーへ確認する。
- 永続化未完了が残る間は、新しい質問、再スキャン、納得ゲート、完了報告へ進まない。
- 永続化未完了による停止は、ベースの「中断終了経路」とは別の技術的停止として扱う。永続化未完了中にユーザーが中断を求めても、通常の中断完了として Step 8 へ進まず、永続化未完了の対象、保存済みの成果物、未反映または未検証の成果物、復旧方法を報告して停止する。未完了が解消された後にのみ、通常の面談再開または中断終了経路へ進める。

## セッション中のドメイン規律（`speckit-grill-me` の面談規律に上乗せ）

- **ドメイン用語集と衝突したら即指摘する。** 質問作成時でも回答で見つかった場合でも、ベースの矛盾確認規律に従う。対象論点を再オープンし、旧確定値を退避し、矛盾を伝え、1 つの決定を問う確認を次ラウンドの先頭に置く。例えば、用語集の「取消」の定義 X を維持するか、新しい意味 Y へ変更するかを問う。別のドメイン決定と抱き合わせたり、固定済みの現フロンティアへ挿入したりしない。
- **曖昧・多義的な語は正準用語へ確定させる。** ユーザーや spec が使う語が複数の概念を指し得るとき、どの概念を指すのかを確認する質問を質問候補一覧に足し、ラウンドで質問して確定させ、プロジェクトの正準用語 1 語に置き換える（例: 「アカウント」が顧客とログイン利用者のどちらも指し得るなら、どちらの概念かを問う）。
- **具体シナリオで概念の境界を確定させる。** 明示された目標・調査済み事実・受諾済み回答が根拠となる状況だけを使い、ベースの候補・深さ・閾値の規則を適用する。説明用のシナリオには「仮定」と明示し、受諾前に事実・決定として保存しない。例えば、返却検収前に機材を再び貸し出すと資料にあるなら、その状況で「返却」と「貸出」の境界を確認する。
- **コードと突き合わせる。** ユーザーの説明と実装が矛盾したら、その矛盾を示す追撃質問を質問候補一覧に足して確認する。実装の現状に関する事実は実コードを一次情報とするが、メモリの記述と食い違う場合は、後述の矛盾確認規律に従い、メモリや spec を黙って上書きしない。
- **用語が確定したらその場でドメイン用語集を更新する。** 用語の定義として、概念の意味と境界、正準の表記、避けるべき同義語を書く。実装詳細は書かない（ドメイン用語集はスペックでも作業メモでもない）。書き込むのは**ユーザーが受諾して確定した内容だけ**で、保留中の回答・仮想シナリオの前提はメモリへ書かない（ベースの面談規律と同じ扱い）。
- **決定記録は、書き分けルールの表にある 3 条件をすべて満たすときだけ作る。** 1 つでも欠けたら作らない。
- **記録済みメモリの内容と矛盾する回答・調査結果は、ベースの「記録済みの決定との矛盾を検知したら」の規律で扱う。** 黙ってメモリを上書きせず、対象論点を再オープン（設計ツリーのノードを未解決へ、カバレッジマップを Partial へ戻し、旧確定値は退避）して、確認の追撃質問を質問候補一覧に足し次ラウンドの先頭で出す。決着後に、旧決定の維持なら退避値を破棄するだけ、変更ならメモリを更新したうえで、対応論点を Resolved へ変更する。
- **中断終了経路に入った場合**（ベースの規律）、確定・保存済みのメモリはそのまま維持し、未受諾の内容は書かない。書き込んだメモリは完了報告に含める。

## 完了報告への追記

`speckit-grill-me` の Step 8 完了報告に、次を加える。

- 書き込んだメモリのパス（更新・新規作成の別）
- 追加・変更した用語／決定の要旨
- 記録済み決定と矛盾したため明示した論点（あれば）
- 納得ゲートで受諾され、知識へ反映した帰結と、その元の決定・事実。中断により未確認のまま残った帰結は区別する
