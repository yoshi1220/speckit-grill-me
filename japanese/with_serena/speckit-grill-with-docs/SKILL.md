# SpecKit Grill With Docs

**必須**: 先に `../speckit-grill-me/SKILL.md` を Read し、その手順に従う。

`/speckit-grill-me` を**ベースとして**実行する。手順（言語設定・前提・Extension hooks・用語集・面談規律・中断終了経路・Workflow Step 1〜8・Behavior rules）、成果物、終了条件はすべて `/speckit-grill-me` のとおり（`/speckit-clarify` 代替としての成果物パリティを含む）。本ファイルで使う用語（論点・論点状態・質問候補一覧・フロンティア・ラウンド・カバレッジマップ 等）はベースの「用語集」の定義に従う。

本スキルがベースへ追加する責務は 1 点だけ — **問答中に確定した用語と、記録条件を満たす業務ドメイン・技術構成の決定を、その場で Serena メモリへ正しく永続化する**こと。以下の追加規律は、すべてこの責務を実現するためのものとする。

ベースの Behavior rules にある「変更してよいのは spec.md と `checklists/requirements.md` だけ」は、本スキルでは**下表のメモリを加えた範囲**に読み替える。plan / tasks / コードを変更しない点は変わらない。

## 書き込み先

このリポジトリのドメイン知識と技術構成の決定は、**Serena メモリ（********`.serena/memories/`********）を正準な記録先**とする。所在の判定・分岐はしない。

| 確定した内容            | 書き込み先                                                                                                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 用語・概念の定義（ユビキタス言語） | `.serena/memories/domain/product_domain_knowledge.md` の該当節。トピックとして大きければ `.serena/memories/domain/<kebab-slug>.md` を新規に切る                                                                                                                               |
| 業務ドメインの設計決定       | `.serena/memories/domain/`（同上の粒度で判断）。後述の記録条件 3 つをすべて満たすものだけ                                                                                                                                                                                            |
| 技術構成の決定           | `.serena/memories/architectures/architecture_patterns.md` の該当節。トピックとして大きければ `.serena/memories/architectures/<kebab-slug>.md` を新規に切る。後述の記録条件 3 つをすべて満たすものだけ（`change-history-design.md` / `error_handling_architecture.md` / `service-opening.md` の前例あり） |

- **書き込み先は上表に限る。** 別のドメイン文書をリポジトリ内に新設しない。
- ベースの「前提」4 で読む Serena メモリには、**`domain/product_domain_knowledge`** **を必ず含める**。加えて、対象 feature に関係するトピック別メモリを読む（後述の衝突検知に必要なため）。
- **読み書きは Serena のメモリツールで行う。** 読み取りは `read_memory`、既存メモリの更新は `edit_memory`、新規メモリの作成は `write_memory` を使う。`memory_name` は上表のパスから `.serena/memories/` と `.md` を除いたもの（例: `domain/<slug>` / `architectures/<slug>`。**`.md`** **拡張子を付けない**）。上表のパスは実体の所在を示すもの。
- 既存メモリを更新するときは、そのメモリの構造を維持して該当節だけを直す。トピック別メモリを新規作成するときは、タイトルを短く安定した決定・概念名にし、冒頭に結論を一文で記載する。関連メモリや根拠となる実装の一次情報パスが存在する場合は併記する。メモリ間の参照は `mem:<name>` 形式で書く（例: `mem:domain/vehicle-category-unified-master`）。存在しない参照や実装パスを推測・捏造して記載しない。
- 書き込みのたびに同じ `memory_name` を `read_memory` で読み戻し、確定内容が重複なく反映され、既存構造を壊していないことを確認する。
- `domain/product_domain_knowledge` を読めない場合、既存の更新先を読めない・書けない場合、または新規メモリを作成できない場合は、他の場所へ書かず、その旨を報告して止める。

## 情報源の権威

情報源の権威は、内容の種類ごとに次のように扱う。

| 内容                      | 正とする情報源                                                   |
| ----------------------- | --------------------------------------------------------- |
| プロジェクト原則                | 存在する場合の `.specify/memory/constitution.md`。他の要件・決定に対する上位制約 |
| feature 固有の要件・期待挙動      | 現在の `FEATURE_SPEC` と、このセッションでユーザーが明示的に確定した決定              |
| feature を超えるドメイン用語・設計決定 | Serena メモリ。ただし、このセッションでユーザーが変更を明示的に確定した場合は、保存・検証後の新しい決定   |
| 現在の実装状態                 | 実コード・スキーマ・マイグレーション・テストなどの一次情報                             |

- constitution が存在する場合、それに反する回答は確定扱いにしない。対象論点を再オープンし、原則に適合する決定を確認する。constitution 自体の変更は本スキルの範囲外とする。
- ユーザーが constitution との矛盾を理解したうえでその決定を維持する場合は、本スキル内では解消不能として対象論点を理由付き Deferred にする。constitution の変更または例外承認が先に必要であることを記録し、constitution に反する内容を spec または Serena メモリへ確定事項として書き込まない。
- ユーザーの新しい回答は、提案・曖昧・矛盾確認中の段階では既存記録を上書きする権威を持たない。ベースの矛盾確認規律を通り、Step 4A と必要なメモリの保存・検証が完了した時点で新しい決定を正とする。
- 現在の実装事実は、それ自体を望ましい要件や設計決定とはみなさない。異なる種類の情報源が矛盾する場合は、どちらかを黙って優先して上書きせず、ベースの矛盾確認規律に従って対象論点を再オープンする。

## 書き分けルール（spec と Serena メモリの二重管理を防ぐ）

| 内容                                | 書き込み先                                                                                    |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| この feature 固有の要件・挙動・エッジケース・受入条件   | ベースの前提で取得した `FEATURE_SPEC`（`/speckit-grill-me` の Step 4A / 4B と Step 4C の反映・検証規則どおり） |
| feature を超えて通用する用語・概念の定義          | ドメイン用語集メモリ（上表）                                                                           |
| 覆すコストが高く、将来の読者が「なぜ？」と思う実トレードオフの決定 | 決定記録メモリ（上表）。次の 3 条件をすべて満たすときだけ: ①覆すコストが実質的に高い ②文脈なしでは将来の読者が驚く ③実際に代替案があり理由をもって選んだ結果である   |

- 同じ内容を spec 本体とメモリの両方で**正準定義として**管理しない。feature を超えて通用する用語の正準定義は Serena メモリだけに置く。spec 本体ではその用語を使い、feature の理解・検証に必要な最小限の文脈や feature 固有の制約は記載してよいが、正準定義そのものを複製・再定義しない。決定は feature 固有の要件・帰結だけを spec 本体へ、feature を超えて残す理由・トレードオフだけをメモリへ書き分ける。ベースの Step 4A が要求する Clarifications の Q/A 行は監査記録なので、この二重管理には数えず省略しない。
- Serena メモリへの書き込みも、spec と同じく**確定のたびに即時保存する**。1 回の回答で複数の用語・決定が確定した場合も 1 件ずつ書いて保存する（まとめ書きしない）。
- Step 4A で確定した 1 件がメモリへの記録対象でもある場合は、spec の保存・検証後、対応するメモリの保存・読み戻し検証を完了してから、その論点を Resolved へ変更して次の質問へ進む。メモリの保存または検証に失敗した場合は Resolved にせず、別の場所へフォールバックせずに停止する。feature 固有の内容だけなら、ベースの Step 4A の順序を変えない。
- ベースの Step 4B だけで確認した実装事実を、業務ドメインまたは技術構成の「決定」として Serena メモリへ昇格させない。実装事実から feature を超える設計判断を新たに記録する必要が生じた場合は、ユーザーが決定すべき論点として質問候補一覧へ追加し、受諾後にだけメモリへ書く。

### 永続化失敗時の扱い

spec と Serena メモリへの反映は単一トランザクションではない。片方の保存後にもう片方の保存または検証が失敗した場合は、その論点に\*\*「永続化未完了」という補助的な永続化状態\*\*を付与して停止する。

「永続化未完了」はベースの論点状態ではない。対象論点の設計ツリー／カバレッジマップ上の状態は Partial のまま維持し、spec と必要な Serena メモリの両方の保存・検証が完了するまで Resolved にしない。

回答の受諾、spec への保存、メモリへの保存・検証、論点の Resolved はそれぞれ別の状態として扱う。

- 停止時に、対象論点、確定内容、保存・検証済みの側、未反映または未検証の側、失敗内容、次に必要な復旧操作を明示する。
- 同一セッションで再開する場合は、新しい質問を始める前に未完了側の保存・検証を終える。保存済み側も読み直し、重複や新しい矛盾がないことを確認してから Resolved にする。
- 新しいセッションでは、Step 1 の質問候補を作る前に、最新の Clarifications にある用語・記録対象決定と関連する Serena メモリを照合する。未反映側を確定内容から一意に再構成でき、既存記録とも矛盾しなければ不足側へ反映・検証する。既存記録と矛盾する場合はベースの矛盾確認規律へ渡し、確定内容を一意に再構成できない場合は推測せずユーザーへ確認する。
- 永続化未完了が残る間は、新しい質問、再スキャン、納得ゲート、完了報告へ進まない。
- 永続化未完了による停止は、ベースの「中断終了経路」とは別の技術的停止として扱う。永続化未完了中にユーザーが中断を求めても、通常の中断完了として Step 8 へ進まず、永続化未完了の対象・保存済み側・未完了側・復旧方法を報告して停止する。未完了が解消された後にのみ、通常の面談再開または中断終了経路へ進める。

## セッション中のドメイン規律（`/speckit-grill-me` の面談規律に上乗せ）

- **ドメイン用語集と衝突したら即指摘する。** 「ドメイン用語集の『取消』は X の定義だが、いまは Y を指しているように見える。どちらか」— 気づいた最初のラウンドで指摘する: 質問を組み立てる時点で気づいた衝突は該当質問の本文に併記し、回答で露出した衝突は追撃質問を作って質問候補一覧に足し、次回以降のラウンドで明示する。衝突を検知した時点で、次回以降のラウンドで確認することをユーザーに 1 行伝える。
- **曖昧・多義的な語は正準用語へ確定させる。** ユーザーや spec が使う語が複数の概念を指し得るとき、どの概念を指すのかを確認する質問を質問候補一覧に足し、ラウンドで質問して確定させ、プロジェクトの正準用語 1 語に置き換える（例: 「アカウント」が顧客とログイン利用者のどちらも指し得るなら、どちらの概念かを問う）。
- **具体シナリオで概念の境界を確定させる。** 2 つの概念の関係が話題になったら、関係を抽象的に聞くのではなく、境界上に乗る具体的な状況をこちらで作って「この場合はどうなるか」を問う質問を質問候補一覧に足す。回答から、どこまでが一方でどこからが他方かの境界を確定させる（例: 「返却」と「貸出」なら「返却された機材が検収前に再び貸し出されたら、どちらの扱いか」を問う）。
- **コードと突き合わせる。** ユーザーの説明と実装が矛盾したら、その矛盾を示す追撃質問を質問候補一覧に足して確認する。実装の現状に関する事実は実コードを一次情報とするが、メモリの記述と食い違う場合は、次の矛盾確認規律に従い、メモリや spec を黙って上書きしない。
- **用語が確定したらその場でドメイン用語集を更新する。** 書くのは用語の定義 — 概念の意味と境界、正準の表記、避けるべき同義語。実装詳細は書かない（ドメイン用語集はスペックでも作業メモでもない）。書き込むのは**ユーザーが受諾して確定した内容だけ**で、保留中の回答・仮想シナリオの前提はメモリへ書かない（ベースの面談規律と同じ扱い）。
- **決定記録は、書き分けルールの表にある 3 条件をすべて満たすときだけ作る。** 1 つでも欠けたら作らない。
- **記録済みメモリの内容と矛盾する回答・調査結果は、ベースの「記録済みの決定との矛盾を検知したら」の規律で扱う。** 黙ってメモリを上書きせず、対象論点を再オープン（設計ツリーのノードを未解決へ、カバレッジマップを Partial へ戻し、旧確定値は退避）して、確認の追撃質問を質問候補一覧に足し次ラウンドの先頭で出す。決着後に、旧決定の維持なら退避値を破棄するだけ、変更ならメモリを更新したうえで、対応論点を Resolved へ変更する。
- **中断終了経路に入った場合**（ベースの規律）、確定・保存済みのメモリはそのまま維持し、未受諾の内容は書かない。書き込んだメモリは完了報告に含める。

## 完了報告への追記

`/speckit-grill-me` の Step 8 完了報告に、以下を加える:

- 書き込んだメモリのパス（更新・新規作成の別）
- 追加・変更した用語／決定の要旨
- 記録済み決定と矛盾したため明示した論点（あれば）

- [ ] 情報源の矛盾が権威ルールとベースの矛盾確認規律に従って解消または終端化されている
